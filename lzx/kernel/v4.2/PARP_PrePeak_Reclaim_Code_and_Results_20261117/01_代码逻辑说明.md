# 最新代码的整体逻辑

## 目标与当前边界

目标是：预测将来缺多少空间，提前回收；在主峰到来前留出足够空闲，同时控制缺页与响应代价。

本版让每个后台应用的一整套操作序列使用一个固定 high；reclaim 负责根据实际缺口、冷热信息、保留量、剩余额度和保护反馈分批回收。每 0.5 秒更新预测和分配，同一次增长段的截止时间不能后移。

这是目前实测的实现，并非“已保证所有场景成功”的版本。最后正式 3 轮中仍有 1 轮未补足。

## 先把几个名词说清

| 名词 | 代码中的含义 |
|---|---|
| WSS | 一个观测时间窗内被访问的驻留页，用作近期活跃内存的估计。参考采集使用 clear_refs 与 smaps Referenced；共享映射计数不是精确物理页并集。 |
| RSS | 进程映射在物理内存中的驻留量，可能含共享映射；不能直接等同于应用拥有的物理内存。 |
| memory.current | 这个 cgroup 当前被计入的总内存，包括匿名页、文件页、内核开销等。空间缺口按这个边界计算。 |
| memory.high | 一直生效的内存压力阈值。超过后，内核可以回收并让应用等待。写入一次，不代表回收只发生一次。 |
| memory.reclaim | 用户态向内核主动提出回收请求。请求量不等于净释放量，也不保证精确选中某些旧页。 |
| refault | 之前离开工作集的页又被访问的相关计数，用来发现回收后重新访问的压力。 |
| PSI | 因资源紧张造成任务等待的累计时间；本版使用内存等待反馈。 |
| 回收预算 | 允许尝试的累计请求上限。窗口更新、暂停恢复都不能把预算补满。 |

## 实际调用顺序

```text
run_total.py
  → 独立采集/复用未触及上限的需求参考
  → 固定测试上限，执行每轮缺口准入检查
  → lab/suite.py 启动相同原生应用和操作序列
  → lab/shared_service.Service 准备同一套校准与执行条件
  → lab/online_service.Service 每 0.5 秒更新预测与计划
  → controller/coordinator.py 分配全局缺口
  → controller/executor.py 执行固定 high 与有界 reclaim
  → 保存运行事件、缺页、响应、占用、接口写入及恢复记录
```

当前原生实验入口是 `lab/shared_service.Service`。它继承 `online_service.py` 的 build/tick 等逻辑；不要把保留的旧兼容初始化路径当作当前实验入口。

## 1. 输入从哪里来

- 预测来自独立参考轨迹的在线回放，当前预测范围默认 20 秒、每 0.5 秒更新；未接入训练模型。
- 预测增长按应用与非应用记账部分对齐相加，保留 cgroup 边界，不把各应用各自最高点直接相加。
- 保护排序与冷对象信息由脚本提供，冷额度受历史候选测量限制；系统没有自动识别用户的操作名称。
- 当前占用、RSS、保护设置、refault、PSI 和前台响应来自运行时读取。

### 为什么需求参考要有较大上限

如果先把实验限制在一个较小 memory.max 内，内核可能已经回收了部分内存，记录到的占用峰值便被压低。拿这个结果当作未回收时的需求，可能算出假性的零缺口。

本版独立需求参考采用 6144 MiB 上限，并要求加载前后 high/max/OOM 事件均不曾出现；被上限影响的参考会被拒绝。它只提供预测数据，不参与开关组评分。开关、校准、正式组都使用同一个较低上限。

本批固定测试上限为 3854 MiB。256 MiB 是按参考峰值选择上限时的目标缺口；由于启动占用会波动，每轮的实际缺口不同，实际准入条件是至少 64 MiB。

## 2. high 怎样确定

`controller/sequence_policy.py::sequence_high` 以整套操作序列的 **WSS 最大值**为基础，同时保留原有安全约束：

```text
固定 high 目标 = 按页向上对齐 max(
    整套序列的 WSS 最大值,
    全序列校准得到的 cgroup 安全保留量,
    起点占用 − 已测试的 high 请求额度,
    当前 memory.min / memory.low
)
```

安全保留的 RSS 与 cgroup 数值成对保存。管理员原有更严格的限制不被放宽，发生冲突则退出控制。

本批目标：GIMP 1538.76 MiB、Calc 359.85 MiB、Firefox 1003.62 MiB。它们不会随 0.5 秒滚动窗口或回收分配量改变。

首次安装如果会引起超过单批/累计预算或保留线允许的收缩，会先推迟安装，由细回收接近目标。保护暂停会恢复原 high，恢复后仍尝试同一个目标。过期计划不能重新安装 high，写入前还会重新读取时钟。

**固定 WSS 目标并不等于峰值期间不会触发 high。** high 限制的是总记账占用；总占用超过它时，内核仍可能回收或限速。本批 Firefox 确实出现这种事件。

## 3. 缺口怎样算

```text
当前空闲 = memory.max − 实际 memory.current
剩余缺口 = max(0, 预测剩余增长 − 当前空闲)
```

预测与反馈使用同一增长口径。两次预测之间重新读取当前空闲时，会减去参考曲线中已经发生的增长，避免把一段旧增长重复计入。

零缺口时不主动 reclaim。high 作为既定上限仍可以存在，因此不能从“没有 reclaim 请求”推断“完全没有内核回收”。

## 4. 回收何时开始、何时停止

`controller/prepeak_timing.py` 从参考占用曲线识别明显上升段，回溯到上升前的低点，作为该段的回收完成截止点，不再拿后面的内存最高点当作截止点。

当前过滤规则用全轨迹振幅的 5% 识别明显增长，回落后持续约 1 秒才结束保护；这些是当前回放实验的过滤参数，已经进入条件指纹，并非统计得到的普适最优值。预测窗口的普适统计尚未完成。

估算整个缺口的回收耗时，使用校准写入记录中有占用下降证据的部分，并受最慢正向批次与完整请求跨度约束；请求量不会直接当成释放速度。估计还包含批次间隔、反馈更新与执行余量。

```text
计划启动时间 = 增长起点 − 补足整个剩余缺口的预计耗时 − 安全余量
```

若时间或容量不足，会从可用时刻尽力执行并记录不可行/未补足量，不通过推迟同一增长段的截止时间来掩盖不足。

每一批真正发出前，会用当前时钟检查“预计结束是否仍在截止前”。来不及就不发。已经进入内核的调用不能强制取消；实际越界会记录完成越界并触发暂停。本批最终 9 轮没有这种越界。

## 5. 每 0.5 秒更新到底更新什么

仍然每 0.5 秒重新取得预测、更新剩余缺口、分配量和保留线。预算、计划起点、整套 high、原始计划到期时间不会重置。

同一次增长段的截止点只能提前；后续预测不能把它推迟到另一个峰值，也不能提前结束该段保护后重新开启回收。上一段保护确实结束、进入下一段可用时段后，才可以准备下一段增长。

计划更新不会取消已经进入内核的调用；并行任务的在途额度单独保留，避免多个应用重复领取同一份缺口。

## 6. 执行与保护

协调器先服务每个应用的定时器和保护，再按保护分从低到高分配。执行器同时检查剩余总预算、接口预算、冷额度、RSS/cgroup 保留量、时间窗和全局剩余缺口。

本批起始批量 8 MiB，逐步增大，单批不超过 32 MiB。refault 或内存 PSI 超阈值会暂停或退出；恢复需要连续安静观测。前台按动作类型设置响应阈值，连续两次超阈值会暂停回收控制。

保护停止的是回收控制，不是结束原生应用任务。应用继续完成负载并接受测量。

运行日志会输出 `DEFICIT_ADMITTED`、`PEAK_SPACE_CHECK`、`RUNTIME_TARGET_UNFILLED`、`RUNTIME_ALERT`、`PROTECTION_EVENT`。未补足、保护暂停、调用越界和应用失败是不同事件，要分别解释。

## 7. 评价时刻不能混淆

本批曲线识别的增长起点约为 1.95、3.48、6.42 秒；它们包括主峰之前较小的增长。多轮没能在这些较早截止点补足。

实验中后台新增数据从约第 8 秒开始，因此结果表另外检查“主峰开始前是否足够”，响应与操作耗时只比较 `[8,22)` 主峰区间。两种检查都保留，不能因为第 8 秒空间足够，就宣称所有较早截止点也都通过。

## 主要文件

| 文件 | 作用 |
|---|---|
| `run_total.py` | 固定批次顺序，独立参考、关闭/校准/正式、源文件冻结及最终恢复 |
| `demand_reference.py` | 未受限参考校验、选择测试上限、每轮真实缺口准入 |
| `inputs_bundle.py`、`execution_contract.py` | 输入索引及条件/源码指纹 |
| `lab/suite.py` | 相同原生应用负载、统一上限、时序、采样和清理 |
| `lab/shared_service.py` | 本协议的共用初始化与资格检查入口 |
| `lab/online_service.py` | 固定 high 缓存、0.5 秒预测更新、细回收计划及实时事件 |
| `controller/prepeak_timing.py` | 增长段、整个缺口耗时、截止锁定 |
| `controller/coordinator.py` | 多应用额度分配与在途请求记账 |
| `controller/executor.py` | 预算、保留线、实时钟检查、内核写入及保护 |
| `controller/native.py` | cgroup v2 原生接口 |
| `total_faults.py`、`total_profiles.py` | 全程总缺页均值比较与校准资格 |
| `lab/root_guard.py` | 有时限、限定四应用 cgroup 的采集辅助程序，结束后恢复 zswap |

`controller/signals.py` 的旧形状分类器保留给兼容调用；当前固定 high/细 reclaim 服务使用显式阶段决策。
