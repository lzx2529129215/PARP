# 复现手册

## 1. 目标

本包的目标不是“重新设计一套新方案”，而是把当前 VM 里已经验证过的 PARP/MGLRU 改动，尽可能完整地迁移到另一台机器上，得到同样的源码、同样的配置、同样的构建产物和同样的运行态检查结果。

## 2. 基线

- 目标基线是 GitHub 上的 `lzx2529129215/PARP` 项目中 `lzx/kernel/v4-parp` 对应的原始内核树。
- 当前包内的 `source/baseline/` 保存了改动前备份，`source/current/` 保存了改动后版本。
- 你可以只靠 `patches/` 复现，也可以直接用 `source/current/` 覆盖比对。

## 3. 复现步骤

1. 获取原始源码树。
   - 推荐把原始 `v4-parp` 内核树放到一个干净目录。
   - 如果已经存在旧 build 目录，先确认没有残留旧产物。

2. 检查补丁顺序。
   - `patches/series.txt` 中的顺序就是推荐应用顺序。
   - 先应用 `mm/vmscan.c`、`mm/memcontrol-v1.c`、`kernel/trace/trace_events.c` 这 3 个补丁，再做构建。

3. 拷贝配置文件。
   - 使用 `configs/current.config` 作为 `.config`。
   - 同时保留 `configs/boot-config-6.17.13-myks-l02` 用于交叉核对。
   - `configs/kernel.release` 必须和最终构建出的 release 一致。

4. 构建。
   ```bash
   bash scripts/build_install_verify.sh /path/to/linux /path/to/build
   ```

5. 重启并检查。
   ```bash
   bash scripts/verify_runtime.sh
   ```

6. 如需二次确认源码是否一致。
   ```bash
   python3 scripts/validate_bundle.py . manifest.json
   ```

## 4. 关键功能说明

### 4.1 `mm/vmscan.c`

这是这次内核功能改动的核心。

- 新增 `parp_memcg_reclaim_bin(struct mem_cgroup *memcg)`。
- 该函数会优先使用 `parp_context_lookup(domain_id, now, &app)` 的 `app_prior_q15`。
- 同时把 `memcg->parp_tier2.limit_bytes` 和 `headroom_bytes` 合并进评分。
- `lru_gen_online_memcg()`、`lru_gen_rotate_memcg()` 和 `shrink_many()` 都改成按这个评分选择 bin。
- 结果是低概率、低余量 memcg 更早进入回收序列。

### 4.2 `mm/memcontrol-v1.c`

这部分补齐了 cgroup v1 的 `tier2_*` 接口，让运行态可以直接看到：

- `memory.tier2_enabled`
- `memory.tier2_alloc_scale`
- `memory.tier2_demote_scale`
- `memory.tier2_alloc_wmark`
- `memory.tier2_demote_wmark`
- `memory.tier2_headroom`
- `memory.tier2_below`
- `memory.tier2_stats`

### 4.3 `kernel/trace/trace_events.c`

这个修改是为了避免 trace event 参数数量很大时，`1ULL << arg` 一类操作触发位移边界问题。
这里加了安全检查和位图访问封装，属于“把调试与观测链路也做稳”的修复，不直接改变 reclaim 策略。

## 5. 运行态确认点

复现成功后，应至少确认以下内容：

- `uname -a` 显示 `6.17.13-myks-l02 #4`
- `tier2_predict_enabled=0`
- `tracefs` 中可见 `parp:*` 事件
- `memory.tier2_enabled` 等 cgroup v1 接口存在
- `dmesg` 里只有已知的 `vmwgfx` / `microcode` 类非 PARP 警告

## 6. 常见问题

### 6.1 `patch` 应用失败

原因通常是源码树不是同一版、已经被别的补丁改过，或者换了 build 目录但没换干净树。
处理办法：

- 先确认是不是原始 `v4-parp` 树。
- 再确认补丁顺序。
- 实在不行，直接用 `source/current/` 覆盖比对。

### 6.2 构建结果和当前 VM 的 release 不一致

大概率是 `.config` 没拷贝对，或者 `LOCALVERSION` 不一致。
需要核对：

- `configs/current.config`
- `configs/kernel.release`
- `scripts/build_install_verify.sh` 里的安装路径

### 6.3 `memory.tier2_*` 找不到

这通常说明：

- 没有启动到新内核
- 不是 cgroup v1 memory 挂载
- 还没把 `mm/memcontrol-v1.c` 的补丁应用上

### 6.4 看到 `vmwgfx` 或 `SRSO/TSA` 告警

这些是当前环境里已知的非 PARP 告警，不代表这次功能失败。

## 7. 难点

- 这套改动不是单文件改动，真正的功能在 `vmscan`、`memcontrol` 和 trace 辅助链路上是串起来的。
- `shrink_many()` 的 bin 选择看似简单，但必须和 memcg 水位线、应用概率和当前回收上下文一起看。
- 如果不保留 `source/baseline/` 和补丁，后续接手人很难精确判断“原来是哪里改了”。
- 只看编译成功不够，必须再看启动态、tracefs、cgroup 文件和 dmesg。

## 8. 结论

这份 bundle 已经把“源码改动 + 构建配置 + 运行验证 + 交接说明”放到一起。按它来，另一台机器可以比较稳定地复现当前代码和功能。
