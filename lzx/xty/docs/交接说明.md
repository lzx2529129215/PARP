  - 将 app prior 和 memcg tier2 headroom 接入 MGLRU memcg/bin 选择

  - 修改 `mm/memcontrol-v1.c`

  - 修改 `kernel/trace/trace_events.c`

源码快照也同时保存：

- `source/baseline/`：改动前备份文件
- `source/current/`：当前可编译运行版本

如果补丁在另一台机器上因为上下文不一致而失败，可以用这两套源码直接人工比对。

## 3. 功能链路

### 3.1 page_alloc 仍负责全局触发

页面分配侧仍然保持 Linux 原生逻辑：

```text
alloc_pages()
  -> __alloc_pages_noprof()
  -> get_page_from_freelist()
  -> zone_watermark_fast() / zone_watermark_ok()
  -> wakeup_kswapd()
```

这部分没有被本次补丁改成应用级策略。全局 watermark 的职责仍然是判断系统是否需要进入回收，以及是否唤醒 kswapd。

### 3.2 vmscan/MGLRU 负责选择回收对象

真正下沉应用信息的位置在 MGLRU 的 node 级回收路径：

```text
balance_pgdat()
  -> shrink_node()
  -> lru_gen_shrink_node()
  -> shrink_many()
  -> shrink_one()
  -> try_to_shrink_lruvec()
```

`shrink_many()` 面向多个 memcg。原始逻辑使用 `pgdat->memcg_lru.fifo[gen][bin]`，先确定 generation，再从随机 bin 起点循环遍历。本次改动保留原始 FIFO/bin 框架，只替换 bin 选择策略。

### 3.3 新增 memcg/bin 评分

`mm/vmscan.c` 中新增：

```c
static unsigned int parp_memcg_reclaim_bin(struct mem_cgroup *memcg)
```

该函数使用两类信号：

- `parp_context_lookup(domain_id, now, &app)` 返回的 `app_prior_q15`
- `memcg->parp_tier2.limit_bytes` 和 `memcg->parp_tier2.headroom_bytes`

分数越低，映射到越靠前的 bin。低概率、低余量 memcg 会更早进入回收；高概率或余量较大的 memcg 会延后。若 `CONFIG_PARP` 未开启、memcg 为 root、PARP mode disabled，逻辑会回退到原始随机 bin 行为。

### 3.4 scan budget 仍负责单 lruvec 强度

本次新增逻辑没有删除 `try_to_shrink_lruvec()` 里已有的 PARP scan budget：

```c
parp_adapter_prepare_scan_budget(...)
parp_adapter_apply_scan_budget(...)
```

当前完整链路可以理解为：

```text
watermark 触发回收
  -> shrink_many 按 app prior + tier2 headroom 选择 memcg/bin
  -> try_to_shrink_lruvec 按 PARP scan budget 调节扫描强度
  -> evict_folios / shrink_folio_list 执行真实页面回收
```

### 3.5 cgroup v1 tier2 接口

`mm/memcontrol-v1.c` 新增 8 个 legacy cgroup 文件：

- `memory.tier2_enabled`
- `memory.tier2_alloc_scale`
- `memory.tier2_demote_scale`
- `memory.tier2_alloc_wmark`
- `memory.tier2_demote_wmark`
- `memory.tier2_headroom`
- `memory.tier2_below`
- `memory.tier2_stats`

这些接口只应在非 root memory cgroup 下出现。验证时不要只看 `/sys/fs/cgroup/memory` 根目录。

### 3.6 trace_events 修复的作用

`kernel/trace/trace_events.c` 修改不是回收策略本身，而是保证 PARP 长 trace event 的打印解析稳定。原有 dereference bitmap 对 `arg` 的位移边界处理不够稳，当前补丁通过 helper 避免 `1ULL << arg` 越界。

## 4. 复现步骤

1. 准备原始 GitHub `v4-parp` 内核源码树。
2. 应用补丁：

```bash
bash /path/to/github/scripts/apply_patches.sh /path/to/linux-source
```

3. 使用当前配置：

```bash
mkdir -p /path/to/build
cp /path/to/github/configs/current.config /path/to/build/.config
```

4. 构建、安装、更新 initramfs 和 grub：

```bash
bash /path/to/github/scripts/build_install_verify.sh /path/to/linux-source /path/to/build
```

5. 重启到新内核后验证：

```bash
bash /path/to/github/scripts/verify_runtime.sh
```

6. 如需确认复现包文件没被改坏：

```bash
python3 /path/to/github/scripts/validate_bundle.py /path/to/github /path/to/github/manifest.json
```

## 5. 运行验证标准

复现成功后至少应看到：

- `uname -a` 包含 `6.17.13-myks-l02`
- `/proc/sys/vm/tier2_predict_enabled = 0`
- `/proc/sys/vm/tier2_predict_latency_ms = 100`
- `/proc/sys/vm/tier2_predict_horizon_ratio = 3`
- `/sys/kernel/tracing/available_events` 中存在 `parp:*`
- cgroup v1 memory 下存在 `memory.tier2_enabled`
- `dmesg` 中存在 `PARP tier2: per-memcg watermarks and EWMA predictor ready (disabled)`

已知非 PARP 告警：

- VMware guest 图形栈可能有 `vmwgfx_bo.c` WARN
- CPU microcode 可能有 `SRSO` / `TSA` mitigation warning

这些告警不代表本次功能失败。

## 6. 可能遇到的问题和难点

### 6.1 源码树在 VM 中不是独立 git kernel 仓库

当前 `/home/xty/v4-parp` 是 GitHub 项目仓库，但 `work/linux-6.17.13-parp` 在这个仓库里表现为未跟踪的完整内核树。因此不能只看 `git status` 判断差异。本包使用 `.bak` 与当前文件生成补丁，这是更准确的差异来源。

### 6.2 补丁应用失败

常见原因：

- 不是同一个原始 `v4-parp` 基线
- 补丁已经应用过
- 源码树被其他人先改过
- 使用了不同内核小版本

处理顺序：

1. 查看 `patches/series.txt`，确认顺序。
2. 用 `patch --dry-run -p1` 检查上下文。
3. 如果失败，直接比对 `source/baseline/` 与 `source/current/`。

### 6.3 构建 release 不一致

通常是 `.config` 没拷贝对，或者 LOCALVERSION 被改变。必须确认：

- `configs/current.config` 已作为 build 目录 `.config`
- `make kernelrelease` 输出 `6.17.13-myks-l02`
- `configs/kernel.release` 与构建结果一致

### 6.4 `memory.tier2_*` 找不到

不要立即判断补丁失败。先检查：

- 是否已经启动到新内核
- 是否使用 cgroup v1 memory 挂载
- 是否在非 root cgroup 下查找
- `mm/memcontrol-v1.c` 补丁是否应用

### 6.5 tracefs 读取权限

`available_events`、`dmesg` 通常需要 root。验证脚本使用 `sudo`，如果没有权限，需要手动以 root 执行。

### 6.6 predictor 默认关闭是正确状态

`tier2_predict_enabled=0` 是安全默认值，表示 EWMA 预测主动回收暂不启用。它不代表 per-memcg 水位线结构不存在。验证水位线应看 cgroup 文件、sysctl 和 dmesg ready 日志。

### 6.7 当前尚未证明性能收益

当前结论是代码和接口正确接入、编译运行通过。尚未证明 direct reclaim、refault、OOM 在真实工作负载下降。后续必须跑带压力的 memcg reclaim 实验，并引入 bin 选择 trace/debugfs 统计。

### 6.8 下一步建议

优先在 `parp_memcg_reclaim_bin()` 增加轻量观测，记录：

- domain_id
- app_prior_q15
- headroom / limit
- final bin
- fallback reason

然后跑有压力的 reclaim 测试，量化“低概率桶先回收”的实际效果。
