# 后续内核修改方向分析

## 1. 输入材料结论

本分析基于 `新增要求` 目录内四个文件：

- `page_alloc.md`
- `vmscan.md`
- `录音.txt`
- `录音适配截图.png`

结论先写在前面：当前新增要求的重点，不是重新设计页面分配水位线，而是把“应用间预测概率”和“每个 cgroup 的水位线”接到 `vmscan.c` 的 MGLRU 回收调度里，尤其是 `shrink_many()` 的 memcg 遍历顺序和回收强度。

## 2. 从录音和截图提炼出的要求

录音里反复强调了几件事：

1. 水位线是按 cgroup 维护的，不是只看全局。
2. 触发回收后，重点要进入 cgroup 内部回收，而不是只停留在全局 `kswapd` 事件上。
3. 真正要改的是 `vmscan.c` 里 MGLRU 的 node 级回收链路。
4. 当前 `shrink_many()` 是按 `memcg_lru` 的 FIFO / bin 结构遍历多个 memcg。
5. 新逻辑要把“应用被再次打开的概率”转成回收优先级，低概率的 memcg / bin 要更早、更强地回收。
6. 录音里提到的 `appbind`、应用名到 memcg 的映射等结构，应该优先复用现有版本里的实现，不要重复造一套路由。

截图示例也印证了这一点：它画的是 `vmscan.c -> shrink_many()` 的位置，说明改动点在 node 级 MGLRU 回收，而不是 `page_alloc` 的分配入口。

## 3. 现有链路应该如何理解

可以把当前链路概括成：

```text
page allocation
  -> zone_watermark_ok / zone_watermark_fast
  -> wakeup_kswapd
  -> balance_pgdat
  -> shrink_node
  -> lru_gen_shrink_node
  -> shrink_many
  -> shrink_one / shrink_folio_list
```

其中：

- `page_alloc.md` 说明了水位线和 `kswapd` 触发机制。
- `vmscan.md` 说明了 `shrink_node()`、`shrink_many()`、`shrink_one()` 以及 MGLRU 的回收框架。
- 录音要求的是：在这条链路里，把“应用预测概率”和“cgroup 水位线”接入回收排序，而不是只在页分配失败后做泛化回收。

## 4. 后续修改方向

### 4.1 水位线继续做触发，不做主策略

水位线的作用仍然是：

- 判断是否进入回收。
- 判断某个 cgroup / memcg 是否已经接近压力边界。
- 给回收强度提供上下文。

它不应该直接决定单页是否回收。单页 / 单 memcg 的优先级，应该交给 `shrink_many()` 里的预测结果和压力状态综合决定。

### 4.2 在 `shrink_many()` 里改遍历顺序

当前 `shrink_many()` 的思路是：

- 取当前 generation。
- 在 `memcg_lru.fifo[gen][bin]` 里遍历。
- 起始 bin 目前偏随机。

新增要求建议改成：

- 先计算每个 memcg 的预测分数。
- 把“未来再次被打开概率低”的 memcg 放到更靠前的位置。
- 如果同一 bin 内有多个 memcg，优先回收低分项。
- 如果某些 memcg 已明显更冷，可以把它们逻辑上并入当前优先 bin，但不要在热路径里做复杂的真实搬迁。

### 4.3 回收强度也要分层

录音里明确提到：“概率低的，又要回收得多，又要有机会被回收。”

这意味着不能只改顺序，还要改强度：

- 低概率 memcg：更早进入扫描，允许更高 reclaim depth。
- 中等概率 memcg：保持普通强度。
- 高概率 memcg：延后扫描，更多保留。

建议把强度和以下信息一起算：

- app 预测概率
- cgroup 水位线余量
- 当前 memcg reclaim 进展
- PSI / direct reclaim 压力

### 4.4 保留公平性和 fallback

不要把 FIFO 结构彻底改成不可逆的硬排序。更稳妥的做法是：

- 在一次回收轮次里做临时评分。
- 只改变本轮的起始 bin / 当前候选顺序。
- 不在 RCU 或热路径里做持久队列重排。
- 一旦预测缺失、压力过高或计分异常，就退回原始 FIFO / round-robin。

这是录音里“合并到这个 bin”“先选低概率桶”的安全实现方式。

## 5. 具体操作建议

### 第一步：确认已有基础

先确认以下能力已经存在或可复用：

- `page_alloc` 的 watermark 和 `wakeup_kswapd` 触发链路。
- `vmscan` 的 `balance_pgdat` / `shrink_node` / `shrink_many` 入口。
- 现有版本里的 `struct appbind`、应用名到 memcg 的映射、概率字段或相关辅助函数。
- 当前已完成的 `tier2` 水位线接口和 effective-tier 框架。

### 第二步：设计 memcg 评分函数

建议新增一个轻量评分函数，例如：

```text
score = w1 * app_future_prob
      + w2 * cgroup_headroom_penalty
      + w3 * reclaim_pressure
      - w4 * recent_reclaim_yield
```

分数越低，越应该先回收。实现时优先用整数或定点数，避免在回收热路径引入浮点和重计算。

### 第三步：改 `shrink_many()` 的起始 bin

把当前随机起始 bin，改成“最低分 bin 优先”，但保留随机回退：

1. 先看当前 generation。
2. 读取各 bin 的聚合分数。
3. 选分数最低的 bin 作为起点。
4. 如果没有足够统计信息，就回退到原随机起点。

### 第四步：在 bin 内做 memcg 细化排序

如果一个 bin 里有多个 memcg，优先扫描：

- 未来打开概率低的 app 对应 memcg
- 水位线更低、headroom 更紧的 memcg
- 近期 reclaim 收益更高的 memcg

### 第五步：增加观测和保护

至少加这些观测：

- 当前 generation / bin 的选择理由
- memcg 的预测概率
- 当前水位线余量
- 本轮 reclaimed / scanned
- fallback 次数

这样后面才能判断是“顺序没选对”，还是“预测本身不准”。

## 6. 建议的落点函数

优先关注这些位置：

- `mm/vmscan.c`
  - `balance_pgdat()`
  - `shrink_node()`
  - `lru_gen_shrink_node()`
  - `shrink_many()`
  - `shrink_one()`
- `page_alloc` 相关水位线触发逻辑
  - `zone_watermark_ok()`
  - `zone_watermark_fast()`
  - `wakeup_kswapd()`

如果需要接入应用概率和 cgroup 信息，再回头补辅助结构和查询接口。

## 7. 验证顺序

建议按下面顺序做：

1. 只加观测，不改行为。
2. 只改起始 bin，不改 bin 内排序。
3. 再加 bin 内 memcg 排序。
4. 最后再调回收强度和 fallback 条件。

验证重点不是“能不能编译”，而是：

- direct reclaim 是否下降
- refault 是否下降
- PSI 是否恶化
- reclaim 是否出现饥饿或长尾
- 高概率 memcg 是否被过度回收

## 8. 最终判断

所以，新增要求的本质是：

> 水位线负责触发，`shrink_many()` 负责按应用概率和 cgroup 压力选择回收对象。

下一步修改方向应当围绕“低概率 memcg 更先回收、回收更强；高概率 memcg 更后回收、更多保护”展开，并且必须保留原始 FIFO / fallback 兜底。

## 9. 当前已落地实现

- `mm/parp/core/watermark.c` 已实现 per-memcg tier2 水位线、EWMA predictor 和默认关闭的 sysctl。
- `mm/parp/adapter/scan_budget_adapter.c` 已把 app 预测、压力等级和 target memcg 接进 scan budget。
- `mm/vmscan.c` 已把 `parp_memcg_reclaim_bin()` 接到 `lru_gen_online_memcg()`、`lru_gen_rotate_memcg()` 和 `shrink_many()`。
- 其中 bin 选择同时参考 `parp_context_lookup()` 的 `app_prior_q15` 和 `memcg->parp_tier2.headroom_bytes / limit_bytes`，低概率、低余量 memcg 会更早进入回收序列。
- 当前运行核版本为 `6.17.13-myks-l02 #4`，已完成编译、安装和重启验证。
- 现阶段的验证结论是：水位线功能已实现，且它仍然作为触发和上下文输入，不是单独替代 MGLRU 的主策略。
- 后续若要再增强可观测性，优先加 bin 选择 tracepoint 或 debugfs 计数器，再跑一次带压力的 reclaim 测试。
