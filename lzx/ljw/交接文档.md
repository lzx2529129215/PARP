# PARP 应用间预测驱动内存回收工作交接文档

## 1. 工作目标

当前工作的总体目标是实现一套面向多应用场景的预测驱动内存回收机制 PARP。

核心思想是：

```text
用户当前应用使用状态
→ Runtime Monitor 捕获前台变化
→ LSTM 预测各 App 下一次进入前台的概率
→ 根据预测概率判断后台 App 的未来重用价值
→ 优先从低概率后台 App 中释放内存
→ 避免错误回收即将重新进入前台 App 的工作集
→ 降低后续 App 切换时的 fault / refault / swap-in / 文件重读开销
```

目前的研究重点在 **App 级回收控制**。

暂时不考虑：

* App 内进程级回收额度分配；
* 页面级预测模型与 MGLRU tier 联动；
* 对 Top-1/Top-3 App 做强制保护。

当前策略调整为：

> 对下一前台概率较低的、已经运行但处于后台的 App，在满足内存需求、安全阈值和回收门控条件时，对其对应 memory cgroup 调用 `memory.reclaim`。

每个 App 的所有进程当前已经放置在同一个 memory cgroup 中，并通过内核 AppBind 表建立 App 与 cgroup 的映射关系。

# 2. 当前总体架构

当前已经形成以下链路：

```text
应用自动化操作
        ↓
Runtime Monitor
        ↓
前台 App / opened_apps / duration 等状态
        ↓
在线 v3 LSTM
        ↓
每个候选 App 的下一前台概率
        ↓
PARP userspace bridge
        ↓
app_bind / app_prior
        ↓
PARP kernel runtime snapshot
        ↓
App 级 reclaim controller
        ↓
低概率后台 App 筛选
        ↓
安全门 / cooldown / reclaim budget
        ↓
AppBind → memory cgroup
        ↓
memory.reclaim
```

当前阶段主要在验证最后一段：

```text
预测
→ 选择 App
→ 构造明确可回收空间
→ memory.reclaim
→ 测量真实释放量及后续恢复代价
```

# 4. 在线 LSTM 当前语义

当前使用 duration-aware v3 LSTM。

输入主要包括：

```text
history_apps
history_durations_s
opened_apps
current_app
时间特征
```

在线预测通过应用事件驱动。

正式实验中应优先保持：

```text
FOREGROUND_TRANSITION
APP_OPEN_STATE_CHANGE
```

作为应用间预测的主要触发来源。

以下事件不能简单理解为“发生就预测”：

```text
APP_MINIMIZE
APP_RESTORE
```

只有它们真正导致前台 App 或 opened-app 状态发生变化时才应成为有效预测触发。

以下事件通常不应直接触发 App 间 LSTM：

```text
PROCESS_START
PROCESS_EXIT
```

尤其是后续增加的 ballast 辅助进程，其启动和退出不能改变 LSTM 的应用序列语义。

# 9. 当前 App 级回收策略

当前确定的控制思路是：

```text
LSTM 概率高
→ 下一步可能重新进入前台
→ 不主动回收

LSTM 概率低
→ 成为后台回收候选

低概率保持稳定
+
系统确实需要释放内存
+
安全条件满足
→ memory.reclaim
```

调用对象：

```text
<App memory cgroup>/memory.reclaim
```

目前：

> 一个 App 内的全部进程都位于同一个 cgroup。

因此现阶段不考虑进程级拆分。

后续如果继续做进程级优化，可以根据进程活跃程度进一步决定 App 内回收分配，但目前暂停该方向。

# 12. Ballast 实验设计

每个 App cgroup 内额外运行一个：

```text
parp_memory_ballast
```

结构：

```text
App cgroup
├── 真实 App 进程
└── parp_memory_ballast
    ├── anon_cold
    ├── anon_hot
    ├── file_cold
    └── file_hot
```

目标不是模拟某个具体 App，而是构造：

> 已知来源、已知热冷状态、与 App 功能无关、能够准确验证是否被回收的页面。

---

# 13. Ballast 页面类型

当前混合工作集包含：

## 冷匿名页

```text
mmap
→ 每页写入
→ 确保真实物理分配
→ 后续停止访问
```

## 热匿名页

```text
mmap
→ 每页写入
→ 后台仍少量访问
```

## 冷文件页

```text
独立测试文件
→ buffered read
→ page cache
→ 后续停止访问
```

## 热文件页

```text
buffered read
→ 后台周期性访问少量页面
```

文件页使用真实磁盘文件，不使用 tmpfs。

第一阶段不构造脏文件页，避免混入 writeback 和 dirty throttling。

---

# 14. Ballast 最重要的约束

## 只允许前台 App 分配

工作集只能在：

```text
ballast 所属 App
==
Runtime Monitor 当前真实前台 App
```

时构造。

同时要求：

```text
AppBind 正确
ballast PID 位于正确 cgroup
```

App 一旦进入后台：

```text
禁止 mmap 新区域
禁止扩大匿名内存
禁止加载新的文件页
禁止重建已被回收冷页面
```

只允许：

```text
保持进程存活
少量访问 hot 区域
读取状态
记录数据
```

这样实验语义为：

```text
App 前台使用
→ 建立工作集

App 后台
→ 不再制造新工作集
→ 原工作集逐渐变冷
→ 等待系统决定是否回收
```
