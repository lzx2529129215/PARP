# v4.2 Tier2 工作集预测水位控制：问题诊断与实现报告

## 1. 问题结论

当前 refault 增加的直接原因不是 fixture 仍未绑定，而是绑定修复后 Tier2 对大工作集产生了更多真实主动回收，但旧 Tier2 只预测“固定 demote 水位多久到达”，不知道下一批应用需要多少内存、其中多少已经驻留。

同 seed 的绑定前后单轮数据显示：

| 指标 | 绑定前 | 绑定后 | 变化 |
|---|---:|---:|---:|
| Tier2 reclaim pages | 60,715 | 118,736 | +95.6% |
| pgsteal | 81,448 | 145,713 | +78.9% |
| pgscan direct | 89,536 | 56,640 | -36.7% |
| file refault | 44,367 | 81,225 | +83.1% |
| major fault | 16 | 25 | +9 |
| effective-tier 实际保护/降级 | 3 / 0 页 | — | 无法抵消提前回收 |

因此原策略确实把 direct reclaim 搬到了后台，但也提前回收了后续会复用的文件页。LSTM 在本轮 43 个有效转移上的 Top-1 为 34.9%、Top-3 为 62.8%，且 10/43 的真实下一应用排在第 8 名以后；不能把每次 LSTM 输出都当成足够可靠的强回收依据。

## 2. 新控制器

服务每秒按相同 App ID 聚合 GUI scope 与 fixture scope 的工作集，使用：

- 全部 anon；
- active file；
- 最多 1/8 inactive file 作为不确定性余量；
- 1/8 EWMA 与 31/32 衰减峰值；
- 当前前台应用的完整估计；
- LSTM 对后续候选应用的概率加权估计。

事件发生时生成：

```text
predicted_workingset = 当前前台 WSS + Σ(P(next_app) × next_app_WSS)
predicted_resident   = 上述集合当前仍驻留的概率加权部分
predicted_growth     = predicted_workingset - predicted_resident
```

该结果与应用预测、前台标志、GUI/fixture cgroup 绑定通过一次 `/dev/myfs` ABI v2 ioctl 原子发布，内核只允许与预测携带的 policy cgroup inode 完全一致的 Tier2 cgroup 使用。

## 3. 三态水位决策

内核内部水位是剩余 headroom。为对应“调低使用量水位线会更早回收”，控制关系是：

| 动作 | 条件 | effective headroom demote | 效果 |
|---|---|---|---|
| `STRENGTHEN` | 预计新增量大于正常 3% 余量，或预计 WSS 越过正常使用量线 | 从 3% 提高，最多 10% `memory.max` | 使用量水位线降低，更早进入有界回收 |
| `NORMAL` | 新增量位于硬线与正常余量之间 | 保持配置值，默认 3% | 按原 Tier2 EWMA 进入回收 |
| `RELAX` | 预计集合已驻留，新增量不超过硬分配余量 | 从 3% 降到 alloc，默认 1% | 使用量水位线提高，减轻/跳过主动回收 |

`memory.max - effective_demote_wmark_bytes` 是等价的 effective 使用量水位线。

## 4. 防止“优化适得其反”的门控

- 编译开关：`CONFIG_PARP_TIER2_WSS_PREDICT`，集中在 LZX PARP Kconfig 菜单，默认 `n`。
- 运行时开关：`vm.tier2_wss_predict_enabled`；设为 `0` 时回到同一内核的原始固定 Tier2 水位。
- 置信度必须至少 50%；置信度综合候选覆盖、每个 App WSS 的采样成熟度与 LSTM Top-3 概率质量。
- `STRENGTHEN` 和 `RELAX` 都要求连续两个 prediction generation 得到相同动作。
- WSS 结果超过 10 秒即失效，即使应用 prior 的 TTL 更长也不能继续移动水位。
- 缺失、过期、低置信度、policy domain 不一致或数据异常统一 `FALLBACK` 到原 Tier2。
- 首轮实测后收紧为：`RELAX` 只能在原始 3% demote 线以上抑制推测性回收；到达原始 demote 线立即恢复 `NORMAL`，不得把后台 Tier2 回收推迟给 direct reclaim。`lzx-note`
- 加强后的 headroom 最多为 `memory.max` 的 10%，单次回收仍最多 1024 页，并保留 250/1000 ms cooldown。

## 9. `#26` 修复与下一轮判定

修复后的 `RELAX` 不再允许穿过原始 demote 线：在水位舒适时仍可取消过早的 EWMA 定时任务；一旦 headroom 到达原始 3% demote，`workingset_raw_action` 保留为 `RELAX` 供审计，`workingset_action` 强制变为 `NORMAL`，effective demote 恢复为原值，并累计 `workingset_safety_overrides`。KUnit 合同覆盖了线以上保持 RELAX、到线转 NORMAL、STRENGTHEN 不受影响三种情况。`lzx-note`

下一次启动 `#26` 后必须复用相同计划再做 OFF/ON/OFF/ON 交替实验。接收条件不是“主动回收越少越好”，而是：

1. ON 的 direct scan/steal 不得高于 OFF 的噪声区间；
2. file refault 与 pgfault 不得恶化，并优先要求下降；
3. WSS prediction、RELAX、STRENGTHEN 和 safety override 必须有非零覆盖；
4. 若只降低 Tier2 reclaim、却提高 direct reclaim，则继续判为失败，不进入 Native/APPLY 正式对比。`lzx-note`

## 11. `#27` 实时 headroom 修复

`#27` 改为先计算：

```text
projected_headroom = current_headroom - predicted_growth
```

- 只有预计增长后会触及 1% hard alloc reserve，或完整预测工作集本身越过正常 usage line，才允许 `STRENGTHEN`。
- 增长大于 alloc 但仍能被实时余量覆盖时使用 `NORMAL`，不提前提高 demote。
- 只有增长不超过 alloc 且预计增长后仍高于原始 demote 时才允许 `RELAX`。
- 原 `RELAX` 到达 3% demote 强制恢复 `NORMAL` 的边界继续保留。

## 13. `#29` 实时退出状态机

`#29` 将动作拆成两层：

1. `workingset_policy_action`：只由新 prediction generation 更新；进入 `RELAX`/`STRENGTHEN` 仍需连续两代确认。

## 15. `#30` STRENGTHEN 独立 APPLY 安全门

`#29` 的实测证明，在 effective-tier 实际保护/降级和 reclaim-bin `rebin_moves` 几乎为 0 时，单独提高 WSS 水位只会扩大近似原生候选上的主动回收。`#30` 因此新增 `vm.tier2_wss_strengthen_enabled`，默认值为 0，并将 WSS 动作拆成以下三层：

1. `workingset_raw_action`：当前实时 headroom 下的原始三态预测。
2. `workingset_policy_action`：经过两代迟滞后批准的预测动作；即使批准了 `STRENGTHEN`，仍保留 shadow 统计。
3. `workingset_action`：实际 APPLY 动作。新开关为 0 时把已批准的 `STRENGTHEN` 钳制为 `NORMAL`，不允许提高 demote 水位；`RELAX` 不受影响，仍可在安全余量充足时减轻或跳过主动回收。

`memory.tier2_stats` 新增 `workingset_strengthen_apply_enabled`，用于从每个 memcg 直接审计安全门状态。KUnit 合同覆盖 `STRENGTHEN + switch=0 -> NORMAL`、`STRENGTHEN + switch=1 -> STRENGTHEN` 和 `RELAX + switch=0 -> RELAX`；当前发布配置未启用 KUnit，所以本轮以生产配置的编译/链接成功和补丁重放校验为静态接收依据，启动后还需要做运行时接口与同种子配对验证。测试 runner 未修改。`lzx-note`
