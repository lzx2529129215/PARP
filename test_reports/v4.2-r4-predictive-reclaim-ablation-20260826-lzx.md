## 1. 结论摘要

1. **应用预测场景已经明显比旧 Test3 更匹配 LSTM。** 在 LSAPP held-out 正向场景中，下一真实切换 Top-1 为 `35/87 = 40.23%`，Top-3 为 `56/87 = 64.37%`；随机负对照降到 Top-1 `20/87 = 22.99%`、Top-3 `44/87 = 50.57%`。旧 Test3 的约 `12.5%/33.3%` 问题得到实质改善。
2. **服务链路已修复并在线生效。** 正向 Native 的 90/90 个 case 切换、正向 Combined 的 90/90 个 case 切换都触发 LSTM，并通过 `/dev/myfs` 成功 `APPLIED`。不再使用 debugfs 下沉预测。
3. **目前真正改变回收行为的仍然只有 Tier2。** Combined 相对 Native 的 cgroup direct scan 平均配对下降 `40.50%`，`memory.events:max` 下降 `74.75%`；这是当前可以确认的 Tier2 收益。
4. **Tier2 的代价大于当前总体收益。** Combined 总 pgscan 上升 `49.40%`，file refault 上升 `204.55%`，major fault 上升 `6.02%`，memcg reclaim 每轮 p95 的均值由 `179 us` 增到 `2505 us`。它把前台同步回收转成了较多提前回收，但当前回收页选择不准，造成随后重新读回。
5. **LSTM/bin 与 effective-tier 尚不能声称带来 pagefault/refault 收益。** Combined 三轮中 bin 有 114 次有效评分、18 次应用上下文评分，但 `rebin_moves=0`；effective-tier 检查 694,643 个候选页，应用上下文只覆盖 434 页，`app_prior_protect_pages=0`、`upgrade_pages=0`、`downgrade_pages=0`。预测到达了内核，但没有转化成足够的实际调度动作。
6. **本轮不能交付“OOM kill 降低率”。** Native 与所有 Apply 组均为 `oom_kill=0`。这是接近 OOM 的安全阈值场景，能比较 `memory.events:max`，但不是牺牲进程式 OOM-kill 场景，分母仍为 0。

因此，本轮最准确的判断是：**LSTM 场景和 `/dev/myfs` 链路已经打通，Tier2 能显著降低 direct reclaim 压力事件；但 bin/effective-tier 的动作覆盖仍不足，Tier2 又回收了过多随后复用的 file page，所以 full APPLY 尚未获得整体 pagefault/refault 收益。**

## 2. 本轮先修复的服务缺口

修复前审计发现：自动化 30 次前台切换全部成功，但常驻服务的长连接 X11 监听在部分轮次只看到首次切换，LSTM 主要由 APP_OPEN/APP_CLOSE 触发。这会让“预测指导回收”的因果解释失效。

本轮增加了以下兜底：

- 原生 X11/GNOME 事件仍为低延迟主路径；
- 每个 1 秒采样周期用真实活动窗口校对事件状态；
- 仅当 App/窗口与状态机不一致时生成 `POLL_FOREGROUND_RECHECK`；
- 补偿事件与迟到的原生事件进入同一状态机，按 App/窗口去重；
- 补偿出的 `APP_SWITCH` 沿原有 LSTM → `/dev/myfs` 路径提交。

验证结果：

- runtime monitor 单元测试：`109 passed, 3 skipped`；
- 专项状态机测试：覆盖“漏切换补偿”和“迟到原生事件去重”；
- 修复后 smoke：12 个 APP_SWITCH（含启动阶段）全部成功预测，30 个 APP_SWITCH/OPEN/CLOSE 预测全部 `/dev/myfs APPLIED`；
- 常驻服务最终状态：`active (running)`；
- 实验结束后开关已恢复常驻默认：PARP mode `1`、effective-tier `0`、Tier2 `0`；
- 本次启动未发现 PARP、myfs、Oops 或 panic 错误。

### 5.1 能确认的收益

- Combined 把 direct scan 从 155,490 降到 92,139 页，配对下降 40.50%。

- Tier2/Combined 通过主动回收新增约 127k—139k 页/轮的 proactive scan；减少的 direct scan 没有抵消这部分工作，总扫描反而增加约 49%。

- memcg reclaim p95 显著增加，说明主动回收虽然从部分前台分配路径移开，但回收批次本身更重。

## 6. 机制动作审计

下表为三轮 counter 差分之和，不是开机累计值。

| 组 | Tier2 reclaim | effective-tier | bin-reclaim |
|---|---|---|---|
| effective-only | 0 | 431,881 candidate pages；77 context hits；489 context candidate pages；0 prior protect/demote；0 upgrade/downgrade | 0 |
| Tier2-only | 183 次；180,943 reclaimed pages（约 706.8 MiB）；3,632,732 cooldown skips；0 no-progress | 关闭 | 关闭 |
| Tier2+bin | 180 次；181,905 pages（约 710.6 MiB）；0 no-progress | 关闭 | 132 lookups；114 scored；18 context/rank scores；96 headroom fallback scores；**0 rebin moves** |
| Combined | 181 次；186,912 pages（约 730.1 MiB）；3,639,209 cooldown skips；0 no-progress | 694,643 candidate pages；138 context hits；434 context candidate pages；0 prior protect/demote；0 upgrade/downgrade | 132 lookups；114 scored；18 context/rank scores；96 headroom fallback scores；**0 rebin moves** |

解释：

- r4 的 250 ms 成功冷却和 1000 ms 无进展冷却有效。183/181 次实际主动回收没有再演化成旧版数十万次 reclaim storm；大量 `cooldown_skips` 是 charge hook 在冷却期内被有界拒绝，不是实际执行了数百万次回收。
- effective-tier 的 app prior 只触达 Combined 候选页的 `434 / 694,643 = 0.0625%`，而且没有一页跨过保护边界。因此 effective-only 指标的正向波动没有动作证据，不能归因于该机制。
- bin 评分已经工作，但预测上下文只占 scored 的 `18 / 114 = 15.79%`，其他 96 次使用父 cgroup headroom 回退；已评分 memcg 在扫描时没有发生动态换桶。它可能影响 memcg 初始入桶，但本轮没有证据证明 LSTM 改变了压力期间的实际桶序。
- 所以当前 Combined 的行为和指标主要由 Tier2 水位驱动，LSTM/bin/effective-tier 只增加少量评分路径，尚未形成足够动作。

## 8. OOM 指标状态

本轮参数是 `target_headroom=192 MiB`、`reclaim_probe=128 MiB`，理论上保留约 64 MiB 安全余量；其目标是稳定触发 `memory.max` 附近的同步回收和 `events.max`，同时避免压力 worker 被 OOM kill。因此：

- 可以比较：`events.max`、direct scan、主动回收页数、refault、major fault、延迟和 CPU；
- 不可以比较：OOM kill 降低率，因为 Native 分母仍为 0；
- `events.max -74.75%` 只能表述为“内存上限命中/同步受阻减少”，不能写成“OOM 降低 74.75%”。

若验收必须交付 OOM 优化率，需要另建独立的 sacrificial OOM 场景：固定受保护 GUI 集合，单独的高 `oom_score_adj` 压力进程将 probe 提高到保护线以上，用 `oom_kill_local`、受保护 App 存活率、首次 OOM 时间、OOM 前 direct reclaim 和恢复时间做 Native/Combined 配对。该场景不能与本轮安全阈值数据混算。

## 10. 验收边界与下一步顺序

本轮所有正式轮次仍标为 `VALID_DIAGNOSTIC`，不是最终 formal pass，原因有三：

1. effective-tier 页面模型 provenance 仍为 `ENGINEERING_FIXTURE_UNTRAINED`；应用间 LSTM checkpoint 是已训练模型，但页面六特征模型还不是训练产物。
2. 每组只有 3 轮，足以定位机制方向，不足以证明小于约 5% 的性能差异显著。
3. OOM kill 基线仍为 0。

建议后续严格按以下顺序继续：

1. 为 bin 增加“预测 generation 改变后实际换桶”的明确 counter/trace，并提高应用 cgroup 上下文覆盖；目标是 `context_hits` 覆盖所有受控 App 且 `rebin_moves>0`，再单测 Tier2+bin。
2. 用训练得到的页面模型替换 `ENGINEERING_FIXTURE_UNTRAINED`，调低 effective-tier 跨边界门槛前先跑 SHADOW，确认 protect/demote 的正负样本和动作率，再开启 APPLY。
3. 将 Tier2 回收量由固定 1024 页上限进一步与 headroom deficit、预测置信度和 refault 反馈绑定；当前每组约 700 MiB 的提前回收明显过量。
4. 在不改变本轮安全阈值测试的前提下，新增独立 sacrificial OOM 配对场景，补齐 OOM kill 交付指标。
5. 动作链路有效后再扩到至少 10 个配对 seed，报告中位数、p95 和置信区间。
