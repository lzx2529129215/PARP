# Linux 6.17.13 PARP v4.2 OOM-THRESHOLD OFF/APPLY 配对报告

日期：2026-08-25  
结论状态：`VALID_DIAGNOSTIC_PAIRED`

## 核心结论

在同一个修复后内核 `6.17.13-parp-lzx-v4.2+ #5`、同一次启动、相同三个 scenario plan 下：

- direct reclaim 扫描量从平均 1,189,766 页降至 969 页，下降 **99.9186%**。
- direct reclaim 回收量从平均 1,188,850 页降至 0 页，下降 **100%**。总回收量基本不变，说明回收工作主要从直接回收路径转移到了非 direct 的 memcg/Tier2 路径。
- 受控 cgroup OOM kill 为 `1.0 -> 1.0`，改善 **0%**。本场景能够稳定产出非零 OOM 指标，但当前 APPLY 没有降低 OOM 次数。
- host/root OOM 始终为 0；六轮 OOM 受害者均为专用压力进程，六个 GUI 应用均完成 30/30 自动化步骤。
- cgroup PageFault 为 `4,504,364 -> 4,505,305`，增加 0.0209%；major fault 增加 0.1492%；file refault 下降 0.0640%。因此本轮**不能声称 PageFault 已有有效改善**。
- memcg reclaim 调用对数下降 81.82%，总耗时下降 8.53%，但单次 p95 从 0.125 ms 增至 1.001 ms，尾延迟恶化 703.21%，后续需要单独处理。

这份数据可以作为后续 Linux 6.17.13 原生源码测试的 v4.2 对照数据，但还不是最终模型收益：effective-tier 模型仍标记为 `ENGINEERING_FIXTURE_UNTRAINED`，且 Runtime Monitor/在线预测输入在本轮关闭。

## 如何理解结果

1. **direct reclaim 指标有效且改善明显。** APPLY 总扫描/回收量与 OFF 基本相同，但 direct 计数接近零，说明 Tier2/主动 memcg 回收提前承担了工作，应用分配线程不再执行大规模直接回收。
2. **OOM 指标有效但没有改善。** 场景按设计保证每轮产生一次 cgroup OOM，APPLY 仍为一次，当前可交付结论是 0% 改善，而不是 N.A. 或无法触发。
3. **PageFault 没有改善。** pgfault、pgmajfault 的变化都在 0.2% 内，不能据此声称优化；file refault 仅下降 0.064%。
4. **memcg 尾延迟是回归点。** 调用次数和总耗时下降，但单次 p95 上升约八倍，说明 APPLY 把工作合并成了更少、但更重的回收批次。
5. **不能把本轮收益归因给训练后的 effective-tier。** 内核报告 `metadata_ready=0`、`model_provenance=ENGINEERING_FIXTURE_UNTRAINED`，effective-tier 的分数路径没有形成真实训练模型证据。combined 同时打开了 PARP/effective-tier/Tier2，direct reclaim 变化更可能来自 Tier2；后续需补 Tier2-only 和 effective-tier-only 消融。
6. **启动延迟改善仅作辅助指标。** 它是 X11 窗口就绪代理而非首帧延迟，且存在应用缓存和运行顺序影响，不能作为核心交付结论。
