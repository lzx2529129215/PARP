# v4.2 预测内存调度链路修正记录（2026-08-26）

## 结论

本轮完成了“先修实验因果关系，再修 bin-reclaim，再修 effective-tier，最后补齐训练与消融入口”的代码修正。r3 已完成干净启动和在线诊断，并在 Tier2 压力烟测中发现主动回收的一毫秒重排风暴。该问题已在
`6.17.13-parp-lzx-v4.2-apply-myfs-guided-r4` 中增加跨调用预算/冷却约束；r4 已编译、安装并设为 GRUB 默认，但尚未重启验证，因此**不提前宣称 r4 已获得性能收益**。

## 1. 先修正预测验证场景

- 新增 `lsapp_heldout`：从 LSAPP 对齐数据的 test split 选择连续、未参与训练的真实切换序列。
- 新增 `random_negative`：保持相同应用集合、压力和随机种子，但让下一应用标签与历史无关，作为“预测无信息”负对照。
- 执行顺序改为：当前应用进入前台并访问热页 → 等待 LSTM 预测和 `/dev/myfs` 下沉 → 启动压力并等待进入稳定保护线 → 切换到真实下一应用并访问热页。
- OOM-THRESHOLD 压力支持按 cgroup 剩余内存（默认 192 MiB）保持，不再要求先把匿名压力进程杀到 OOM 才开始应用切换。
- 场景计划记录 test split 路径、SHA-256、原始 session、时间戳、历史应用和 dwell，保证 OFF/APPLY 可按同一计划重放。

配置入口：`test/test/parp-predictive-reclaim-config-lzx.json`。

## 2. 修正 bin-reclaim 没有有效分桶的问题

旧逻辑把应用概率与父 cgroup 剩余水位取最小值。在 3% 左右 headroom 下，所有应用都被压到 bin 0，LSTM 排名实际上被抹掉。

修正后：

- cgroup headroom 只控制 Tier2 是否触发以及回收强度；
- 有 `/dev/myfs` 应用上下文时，按 LSTM rank 映射到 8 个有序 bin；
- 没有应用上下文时才退回 headroom score；
- 预测 generation 更新后，仍停留在旧 bin 的 memcg 会先重分桶，再参与扫描；
- `reclaim_bin_stats` 新增 rank score、headroom fallback、rebin moves 和 8 个 score-bin 计数。

这样可以直接验证“预测是否进入多个 bin”以及“预测更新后是否真的移动了回收队列”，不再只看一个模糊的 context hit。

## 3. 修正 effective-tier 只有保护、没有预测性释放的问题

旧 app prior 只会给高概率应用加正偏置，无法让低排名应用中原本处于保护边界的页面恢复为可回收候选；Combined 因此容易增加保护和扫描成本。

修正后 app prior 为有界双向偏置：

- 前台或 rank 1–2：较强热偏置；
- rank 3–4：较弱热偏置；
- rank 5–7：概率校准的中性/正偏置；
- rank 8 及以后：冷偏置，只允许在原生保护边界、连续两次候选、预算和安全门都满足时下调一级；
- 严重压力只禁止新增升级保护，不再禁止有界冷降级。

新增统计可区分 hot-bias、cold-bias、真正改变保护的页数和真正恢复回收的页数。

## 7. 重启后的验证顺序

1. 验证 `uname -r` 为 r4，检查启动日志、`/dev/myfs`、user service、Tier2 cooldown 统计和新增 debugfs 统计文件。
2. 用相同 seed 先跑 `native` 与 `lsapp_heldout`，建立同一二进制全关基线。
3. 依次跑 `effective`、`tier2`、`tier2_bin`、`combined`；每组重放 native 的 scenario-plan。
4. 用 `random_negative` 重跑完整 APPLY，判断收益是否真的依赖预测信息，而不是仅来自提前回收。
5. 单独跑 `shadow_train`，通过零丢失门后生成页面数据；训练得到的新模型不能自动覆盖内核静态模型，必须经过离线 held-out gate。
6. 主要结果报告同时给出预测窗口内 major fault、file refault、direct reclaim stall、前台切换 p95/p99，以及 bin/tier 的实际动作计数。

只有当 `lsapp_heldout + APPLY` 优于其配对 native，且优势在 `random_negative` 中明显衰减，才能把收益归因给 LSTM 引导的 bin-reclaim/effective-tier；否则仍应归因于 Tier2 提前回收或场景噪声。

## 8. r3 在线诊断与 r4 Tier2 限界修复

r3 的 512 MiB 有界越线探针在 Native 下有效，三轮完整基线均为 `VALID_DIAGNOSTIC`：平均 pgscan 328,711、pgsteal 315,911、file refault 209,933、major fault 14.67，30/30 应用切换完整且没有 OOM。effective-tier 三轮也完整，但每轮约 32 万候选页全部保持原决策，upgrade/downgrade/protect/demote 均为 0，说明当前工程 fixture 页面模型尚未产生有效 tier 动作。

Tier2-only 在相同压力下出现两个可重复故障：

- 512 MiB 探针只完成 192 MiB 后 pressure worker 被 memcg OOM，后续序列无法保持同等压力；
- 将探针降到 128 MiB 后，仍在 1/8 用例内产生 61,098,811 页扫描、9,386,495 次 file refault、10,029 次 major fault 和 208,511 对 memcg reclaim trace，最终应用窗口不可用。

源码根因是旧实现只限制单次回收最多 4096 页，但回收完成后会再次采样；只要 headroom 仍低于 demote watermark，就会在 1 ms 后重新排队，缺少跨调用预算或无进展退避。r4 修正为：

- 单次最多主动回收 1024 页；
- 有回收进展后冷却 250 ms；
- 零进展后冷却 1000 ms；
- charge hook 在冷却期间禁止重新排队；
- `memory.tier2_stats` 新增 cooldown deadline、skipped rearm、no-progress 计数。

r3 的 Tier2 失败轮次只作为修复前诊断证据，不进入 Native/APPLY 性能对比。r4 启动后先重复 128 MiB Tier2 烟测，必须同时满足用例完整、主动回收调用有界、无应用 OOM，之后才重新建立全新的 Native 配对基线和消融结果。
