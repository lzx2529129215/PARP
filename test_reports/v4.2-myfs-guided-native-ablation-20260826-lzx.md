# v4.2 myfs-guided APPLY 与 Linux 6.17.13 Native 对比及消融报告

测试日期：2026-08-26（Asia/Shanghai）

## 1. 结论

本轮已经证明 `/dev/myfs` 下沉的 LSTM 应用间预测同时进入了 bin-reclaim 和 effective-tier 页面保护路径，但当前结果只能判为**诊断级有效**，不能宣称已经稳定降低 PageFault 或 OOM。

最可靠的稳态结果是 seed `20260822`、`20260823` 的配对均值：

| 指标（越低越好） | Native | Full APPLY | 相对变化 | 结论 |
|---|---:|---:|---:|---|
| PageFault | 4,504,808.50 | 4,508,708.50 | **+0.09%** | 基本持平、略差 |
| Major Fault | 896.50 | 906.00 | **+1.06%** | 略差 |
| file refault | 459,513.00 | 454,320.00 | **-1.13%** | 小幅改善 |
| 总 pgscan | 1,199,918.00 | 1,217,993.00 | **+1.51%** | 略差 |
| direct pgscan | 1,199,918.00 | 1,216.00 | **-99.90%** | 显著转移出 direct reclaim |
| memcg reclaim 时间 | 311.80 ms | 381.69 ms | **+22.41%** | 变差 |
| 测试 cgroup CPU | 17.08 s | 22.82 s | **+33.61%** | 变差 |
| 启动就绪代理延迟 | 2,687.61 ms | 4,072.77 ms | **+51.54%** | 变差 |
| cgroup OOM / OOM kill | 1 / 1 | 1 / 1 | 0 | 没有改善 |
| failure_total | 1 | 1 | 0 | 没有改善；均为设计内 OOM kill |

因此，当前 Full APPLY 最确定的效果是：**Tier2/bin 将大部分回收从分配路径的 direct reclaim 转成了有界主动回收**。它没有降低总 PageFault，也没有降低设计为必触发一次 kill 的 OOM 指标；tier 保护只带来约 1% 的 refault 改善，尚不足以覆盖额外扫描、评分和调度开销。

### 5.1 解释

1. **Tier2+bin 的核心收益是改变回收来源，而不是减少总回收。** direct pgscan 从约 120 万页降到约 1,160 页，但总 pgscan 反而增加 1.37%。原本发生在内存分配路径中的 direct reclaim，被提前转成了 proactive reclaim。
2. **effective-tier-only 有很小的页面质量收益。** 稳态 file refault 和总扫描分别下降约 0.65% 和 0.48%，Major Fault 下降约 0.39%；但 memcg reclaim 时间、CPU 和启动代理延迟均明显上升。
3. **Full APPLY 保留了 Tier2 的 direct reclaim 转移，并把 file refault 改善扩大到 1.13%，但没有形成端到端收益。** Major Fault、总扫描、CPU 和启动延迟均比 Native 更差。
4. **OOM 没有改善。** 当前 OOM-THRESHOLD 场景就是持续增压直到杀死 `oom_score_adj=1000` 的压力进程，所以每轮 Native/消融/Full 都固定出现 1 次 OOM、1 次 kill、`failure_total=1`。它证明 OOM 指标可观测，但无法仅凭 kill 次数证明优化；还需要比较首次 OOM 时间、OOM 前完成步骤、同负载下是否避免 kill 等指标。

## 8. 为什么 Full APPLY 没有叠加出更大收益

1. Tier2 先执行主动回收，已经改变了进入 MGLRU 扫描的页面集合和回收时机；effective-tier 面对的是被 Tier2 处理后的剩余候选，而不是与 Native 完全相同的候选集合。
2. tier 保护会跳过少量预计即将复用的页面。为了达到同一回收目标，扫描器可能继续检查更多页面，因此 Full 的总 pgscan 高于 Tier2-only 和 Effective-only。
3. app prior 目前是“广泛加 bias、极少跨阈值”：Full 中 288,682 页得到 bias，但只有 92 页真正改变保护结果。信号对决策的有效密度太低，无法覆盖上下文查询、页面评分、状态维护和额外扫描成本。
4. effective-tier 页面复用模型仍标记为 `ENGINEERING_FIXTURE_UNTRAINED`。LSTM 应用间 checkpoint 已实际加载，但页面六特征模型不是正式训练模型，因此 runner 正确地将结果标记为 `VALID_DIAGNOSTIC`，不是正式验收结论。

## 9. 冷启动偏差与无效轮次

Native 的 seed21 是启动后的冷缓存轮次；Full APPLY 的严格有效 seed21 是在此前测试后补跑的热缓存轮次。直接平均会把这个差异误认为约 35% 的 Major Fault 改善。

#19 启动后的第一次 Full seed21 在缓存次序上更接近 Native，但由于 trace 缓冲溢出 31,421 条而按规范判为 INVALID，不进入主均值。其 cgroup 计数显示：Major Fault 2,814、file refault 884,764、总 pgscan 3,752,043，均差于 Native 冷轮的 2,353、646,665、1,818,509。这说明当前不能把三 seed 原始均值中的大幅下降解释为内核收益。

下一轮正式配对应在 Native 和 Full APPLY 各自干净重启后，以相同顺序运行 seed21/22/23，并从一开始使用 64 MiB/CPU trace 缓冲。主结论应同时报告“冷启动 seed21”和“稳态 seed22/23”。
