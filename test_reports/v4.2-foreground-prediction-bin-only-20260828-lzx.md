# v4.2 前台预测 + bin-reclaim 单因素实验

## 1. 实验目的

只验证一条机制链：常驻 service 监听前台应用事件并调用 LSTM，经 `/dev/myfs` 下沉应用排序，内核用该排序改变 MGLRU memcg-bin 的放置和扫描顺序。effective-tier、Tier2 主动回收、WSS 水位调节及其 `STRENGTHEN` 全部关闭。`lzx-note`

此前的 `tier2_bin` 同时依赖 `vm.tier2_predict_enabled=1`，会把 Tier2 主动回收与 bin 排序混在同一处理组中，无法回答 bin 本身是否有效。`#31` 新增独立开关 `vm.parp_reclaim_bin_enabled`，默认 0；bin 排序不再开启 Tier2 全局开关。`lzx-note`

## 2. 唯一处理变量

| 控制项 | bin_off | bin_apply |
|---|---:|---:|
| 常驻前台事件监听、LSTM、`/dev/myfs` | 1 | 1 |
| PARP mode | 2（APPLY；通用页面适配器仍为 native/inert） | 2 |
| `vm.parp_reclaim_bin_enabled` | **0** | **1** |
| effective-tier mode | 0 | 0 |
| `vm.tier2_predict_enabled` | 0 | 0 |
| `vm.tier2_wss_predict_enabled` | 0 | 0 |
| `vm.tier2_wss_strengthen_enabled` | 0 | 0 |
| `memory.tier2_enabled` | 1，仅作为测试 slice 作用域标记 | 1，仅作为测试 slice 作用域标记 |

Tier2 的采样、预测和 delayed-work 入口均先检查 `vm.tier2_predict_enabled`；全局值为 0 时，即使 cgroup 作用域标记为 1，也不会执行 Tier2 主动回收。OFF/APPLY 两组唯一不同项是 bin 开关。`lzx-note`

## 3. 场景设计

采用现有 `peak/full` 的 LSAPP held-out 30 步序列，seed 固定为 `20260826`。六个免登录 GUI 应用在独立、已绑定 app id 的子 cgroup 中保留各自工作集；每步流程为：

1. 前台切换事件触发 service 调用 LSTM，并原子下沉 app prior、rank、foreground 和 cgroup binding。
2. 等待预测稳定后，在 6 GiB 父 slice 内执行 OOM-THRESHOLD 有界压力，压到 192 MiB headroom，迫使 MGLRU 在多个应用 memcg 之间选择回收对象。
3. 访问本步目标应用的文件/匿名工作集，测量预测热应用是否因处于较高 bin 而减少 refault、Major Fault 和启动恢复延迟。
4. 所有轮次复用完全相同的 `scenario-plan.json`，不重新随机生成应用序列、压力大小或停留时间。

该场景针对的是应用间选择：如果只有单个 memcg，bin 排序没有选择空间；如果没有到达回收压力，bin 也不会产生有效动作。因此必须同时满足“多个持久应用 cgroup + 前台预测变化 + 受控父 cgroup 压力”。`lzx-note`

本次启动后 `/proc/meminfo` 的 `MemTotal` 实际为 `16,729,944,064` bytes（约 15.58 GiB），不是 32 GiB。原 8 GiB slice 与 8 GiB 主机保护线没有可行余量，预热轮在 0/30 步即被 `MEMAVAILABLE_HARD_FLOOR` 安全中止。因此正式轮统一使用 [parp-bin-only-config-lzx.json](/home/lzx/Desktop/PARP/test/test/parp-bin-only-config-lzx.json) 的 6 GiB `memory.max`、6 GiB `MemAvailable` 保护线、`memory.swap.max=0`；逻辑工作集为 `2,676,791,048` bytes。两组都达到完全相同的 6 GiB `memory.peak`。`lzx-note`

## 5. 有效性与接收条件

机制有效性必须先于性能结论：

- `/dev/myfs` ABI v2 READY，service 的 foreground/LSTM 提交和 app binding 均有非零覆盖。
- `bin_apply` 的 `apply_enabled=1`、`context_hits>0`、`scored>0`，且 score 不得全部坍缩到同一个 bin。`rebin_moves` 单独报告但不作为每轮必要条件：新进入/自然轮转的 memcg 会直接按预测分数选择 bin，只有已在旧 bin 中的 stale 节点迁移才增加 `rebin_moves`。
- `bin_off` 的 `apply_enabled=0`，两组 Tier2 reclaim invocations/pages 均应为 0。
- 每轮 30/30 步完成，trace loss、自动化失败、策略漂移和非预期 OOM 均为 0。

主要结果指标为 `workingset_refault_file`、`workingset_refault_anon`、cgroup `pgfault/pgmajfault`、trace user fault 和目标应用恢复/启动 P95；同时报告 pgscan/pgsteal、direct reclaim、PSI、CPU、I/O 和场景时长，防止把 refault 改善换成更高扫描或前台延迟。首轮诊断要求方向一致且不系统性退化；只有增加到至少 5 个有效配对后，才对 10% 以上改善作稳定收益声明。`lzx-note`

## 7. 实测结果

### 7.1 数据有效性

10/10 个正式轮均满足：30/30 步完成、`validity.valid=true`、自动化失败 0、trace loss 0、应用异常 0、OOM/OOM-kill 0、相同 plan SHA、相同 6 GiB `memory.peak`。运行内核为：

```text
Linux 6.17.13-parp-lzx-v4.2-apply-myfs-guided-r4+ #31
SMP PREEMPT_DYNAMIC Fri Aug 28 10:54:03 CST 2026
```

隔离检查在所有轮均成立：`parp_mode=2`、effective-tier mode=0、`tier2_enabled=0`、WSS=0、WSS strengthen=0；cgroup 的 `memory.tier2_enabled=1` 只作为作用域标记。Tier2 的 samples、predict scheduled/executed、reclaim invocations/pages 均为 0；effective-tier 的 candidates、scores、upgrade/downgrade/protect pages 均为 0。`lzx-note`

### 7.2 service、LSTM 与 `/dev/myfs` 证据

正式计分时段（11:25:08—11:41:58）的常驻 service 记录为：

| 证据 | 数值 |
|---|---:|
| 前台事件 | 1,068（356 次 switch + 356 focus-in + 356 focus-out） |
| LSTM 调用 | 534/534 success，平均模型推理 4.028 ms |
| `/dev/myfs` 提交 | 534/534 `APPLIED`，ioctl 成功率 100%，ABI v2 |
| 带有效 cgroup binding 的提交 | 519/534（97.2%），总 bindings 5,581 |
| 与 PEAK_CASE_START 因果对齐 | 297/300 个 case 有 10 秒内的直接切换预测 |
| 在线 case Top-1 / Top-3 | 103/297 = 34.68%；169/297 = 56.90% |

因此本轮不是“service 没启动”或“预测没经字符设备下沉”。Top-1/Top-3 是把每个 `PEAK_CASE_START` 与其前一条 10 秒内 `direct_app_switch` LSTM 输出对齐得到的在线场景结果，不是离线训练准确率。`lzx-note`

合计还有 policy hits=407、inherited hits=383；132 个 scored 候选的八 bin 分布为 `[7,17,19,27,20,2,20,20]`，没有坍缩。但是 `scored/lookups=17.3%`，其余 631/763（82.7%）走 fallback。可进一步分解为：356 次 lookup 没有命中开启 scope marker 的祖先，另外 275 次已经命中 policy scope、却没有命中该 leaf memcg 的有效 app context；headroom fallback 在 bin-only 隔离轮为 0。也就是说，预测已到内核、bin 也确实按分数动作，但真正回收候选命中可评分应用上下文的覆盖率仍偏低；这是当前收益不稳定的首要实现线索。`lzx-note`

### 7.6 direct/memcg reclaim

- cgroup `pgscan_direct` 均值：OFF 76,975，APPLY 76,412.8（-0.73%）；`pgsteal_direct`：27,482 对 26,784.2（-2.54%）。
- trace 的 `memcg_reclaim` 配对次数：245 对 237（-3.27%）；总耗时：27.941 ms 对 29.696 ms（+6.28%）；P95：159.6 µs 对 154.0 µs（-3.51%）。
- trace 的全局 `direct_reclaim_begin/end` 为 0，但 cgroup `memory.stat` 明确记录上述 `pgscan_direct`。两者不是同一个采集口径，不能据 trace=0 推断本轮没有 memcg direct reclaim。
- swap-in/out、OOM、OOM-kill 均为 0；该结果只验证预测 bin 排序，不承担 OOM 指标交付。`lzx-note`

### 7.7 结论

**机制通过，性能不通过。** 前台事件→LSTM→`/dev/myfs`→内核 bin 的完整链路已启动并产生真实动作；Tier2、effective-tier、WSS 等其他优化确定没有参与。但是当前数据不支持“前台预测 + bin-reclaim 降低 fault/refault”：page fault 基本不变，refault 方向不稳定，CPU 和前台恢复延迟反而退化。

现阶段最可信的原因按优先级为：

1. 内核可评分覆盖率只有 17.3%，多数真实回收候选没有命中预测上下文而 fallback，预测指导范围不够。
2. 在线场景 Top-1 34.68%、Top-3 56.90%，虽明显高于此前不对齐场景，但仍有大量错误排序；错误地把将复用应用放低 bin 会直接增加 refault。
3. 相同应用序列不等于相同文件页缓存状态，APPLY3 的 1,717 major faults 证明冷/热页状态仍是主要方差源。
4. bin 只改变 memcg 选择顺序，不控制总回收预算；即使少扫约 0.8%，也不足以抵消评分、查找和错误排序的 CPU/延迟成本。

下一步不应打开 Tier2 或 effective-tier。应先给每个 bin lookup 记录“候选 cgroup/app id、binding 命中/未命中原因、预测 generation/TTL、最终 bin”，把 82.7% fallback 分解清楚；同时在每对轮次前固定清理或预热同一组 fixture 文件页，并使用多个独立 seed。只有单点在这些条件下稳定降低 refault 且不增加前台延迟，才进入下一个优化点。`lzx-note`
