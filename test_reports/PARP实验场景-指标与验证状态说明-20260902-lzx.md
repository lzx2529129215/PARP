# PARP 实验场景、指标体系与验证状态说明

日期：2026-09-02  
适用范围：Linux 6.17.13 Native 与 PARP r11 的预测引导内存回收实验  
文档目的：用于向评审者说明“实验在验证什么、怎样验证、看哪些指标、已经证明什么、还有什么没有证明”。

## 1. 一句话概述

本项目验证的是一条完整的跨层链路：桌面应用切换事件进入常驻服务，LSTM 根据最近的应用序列预测后续重入概率，预测与应用 cgroup/workload profile 通过 `/dev/myfs` 下沉到 PARP 内核，内核再据此调整 reclaim-bin 和页面类型选择，最终观察回收来源、缺页恢复、交互响应、公平性和 OOM 生存结果。

实验不是只看“模型预测是否正确”，也不是只看“内核计数是否增加”。完整验证被拆成四层：

| 验证层 | 核心问题 | 主要证据 | 当前状态 |
|---|---|---|---|
| 预测链路 | GUI 序列是否触发了预期 LSTM 输出 | 历史序列、概率、排名、时间戳 | 已通过训练集对齐场景验证 |
| 内核机制 | 预测是否真正下沉并改变回收选择 | `/dev/myfs`、App ID/cgroup 绑定、bin/workload 内核计数 | 已通过 |
| 用户收益 | 少回收热应用能否降低重返时的恢复成本 | major fault、refault、swap-in、串行恢复延迟 | R2–R7 已形成不同强度的证据 |
| 鲁棒性 | 错误预测、多个应用竞争和 OOM 时是否仍可控 | Jain 指数、错误预测代价、OOM victim 数与归因 | R7 已验证；R8 正在校准 |

## 2. 被验证的系统链路

```text
真实 GUI 启动、操作和窗口切换
          │
          ▼
runtime_monitor 常驻服务
  ├─ GNOME D-Bus / 原生 X11 事件
  ├─ 应用生命周期与前台状态
  ├─ 最近 5 次应用历史上的 LSTM 推理
  └─ cgroup anon/file/file_dirty 工作集画像
          │
          ▼
/dev/myfs ABI v3（PARP 组）
  ├─ App ID 与应用 cgroup 绑定
  ├─ 重入概率与排名
  └─ workload profile 与 TTL/generation
          │
          ▼
PARP r11 reclaim
  ├─ reclaim-bin：调整应用子树扫描顺序
  ├─ cold path：优先处理明确低概率应用
  └─ workload-aware：按 ANON_HEAVY / FILE_CLEAN /
                      FILE_DIRTY / MIXED 调整回收倾向
          │
          ▼
cgroup、VM、I/O、trace 与 GUI 响应联合取证
```

Native 组仍运行相同的 GUI 自动化、runtime service、LSTM 和采集逻辑，以尽量保持用户态开销一致；由于 Native 内核没有 `/dev/myfs` 接口，预测不参与内核决策。

本阶段 PARP 正式组主要验证 `reclaim-bin + cold/workload-aware reclaim`。R6/R7 中 `effective-tier`、全局 Tier2 和 Tier2 WSS 调节均关闭，因此不能把结果归因于这些机制。

## 3. 当前自动化与运行环境

### 3.1 当前真实 PC 路径

- 宿主桌面是 GNOME Wayland，真实 PC runner 从 systemd 用户环境取得 `DISPLAY=:0` 和 Mutter Xwayland 的 `XAUTHORITY`。
- runner 对应用设置 `GDK_BACKEND=x11`、`MOZ_ENABLE_WAYLAND=0` 并清空 `WAYLAND_DISPLAY`，让被测 GUI 应用通过宿主 Xwayland 接受自动化。
- 自动化由 JSON `scenario.json` 驱动，支持启动、等待窗口、切换、按键、输入、点击、拖动、滚动、文件打开、窗口状态、前台校验、画面稳定检测、cgroup page-in 稳定检测和清理。
- `xdotool` 是窗口查找、焦点、键鼠输入的主路径，不是 Dogtail 失败后的 fallback；`wmctrl` 用于部分窗口状态操作，`xclip` 用于确定性剪贴板输入，`ydotool` 只用于少数 GNOME compositor 级搜索动作。
- AT-SPI bus 和 `pyatspi` 在系统中可用，但当前场景没有 Dogtail 调用，系统 Python 也未安装可导入的 `dogtail`。因此当前不能描述为“Dogtail/AT-SPI 主控”。
- 每个应用通过 `systemd-run --user --scope` 放入独立的 `automation-<app>.scope`，所有应用 scope 再挂到本轮实验 slice 下。这样 GUI 窗口、进程、预测绑定、内存统计和 OOM 归因面对同一个应用 cgroup。

### 3.2 可选隔离路径

仓库还保留两类嵌套 X11 入口：

| 入口 | 默认 X server | 窗口管理器 | 用途 |
|---|---|---|---|
| 旧 Test1/Test2 | Xephyr | Openbox | 可见、隔离、便于复现实验事件 |
| LSAPP-expanded | Xvfb | Openbox | 无头长时运行，减少宿主锁屏/重认证干扰 |

Test2 默认从 `:3` 开始选择显示号，但如果 socket/lock 已存在会递增到下一个空闲显示，因此它也不是严格固定的 `:3`。当前 R1–R8 真实 PC runner 使用宿主 `:0`，并非始终运行在 Xephyr/Openbox 内。

### 3.3 应用与资产

R1–R7 使用 8 个免登录 GUI 应用：

| 角色 | 应用 |
|---|---|
| 预测热应用 | Firefox 功能域（实际使用 Epiphany）、Thunderbird、VLC |
| 预测冷应用 | GIMP、LibreOffice、Evince、Image Viewer、Solitaire |

R8 扩展到 15 个应用，新增 Audacity、Rhythmbox、Shotwell、Files、Calculator、Calendar、System Monitor，共 1 个压力发起者和 14 个候选 victim 应用。

所有正式动作使用离线、带哈希的固定资产和每轮独立 profile，例如本地 HTML、EML、WAV、ODT、PDF、高分辨率图片和文件目录。网络、账号内容和在线页面不进入工作负载。

## 4. 实验矩阵

当前实验由两部分组成：受控页级机制场景负责精确构造页面状态，R1–R8 真实 GUI 场景负责验证更接近用户操作的结果。二者互补，不能互相替代。

### 4.1 受控页级五场景

| 场景 | 要回答的问题 | 核心操作 | 主要判据 | 当前结论 |
|---|---|---|---|---|
| 受控 1：冷应用退出 | 后续不再使用的应用能否优先回收 | 8 个应用 scope 内建立固定文件工作集，冷应用使用一次后退出前台序列 | 冷/热回收占比、热应用误回收量 | 通过 |
| 受控 2：预测即将返回 | 应用级预测热能否保护页面级冷页 | 压力后精确重读 Firefox 的 128 MiB 文件区间 | file refault、major fault、direct scan、首次复用耗时 | 通过 |
| 受控 3：多应用来源分布 | 固定回收任务究竟来自哪些应用 | 多热/多冷应用并存，精确比较逐应用 `mincore()` 驻留下降 | 冷来源占比、逐应用回收量、总回收等量性 | 通过 |
| 受控 4：冷脏替代热干净 | 冷脏页能否替代热干净页；增强是否总有收益 | 精确构造 clean/dirty/hot inode 池 | 热页保留、冷脏回收、refault、PSI、swap、pgscan | bin-only 通过；无条件 cold-aggressive 不合格 |
| 受控 5：写回受限门禁 | 初始 `may_writepage=0` 时增强是否有边际价值 | 临时设置 `vm.laptop_mode=600`，构造冷干净页不足、冷脏页足够的缺口 | `writepage_promotions>0`、热页 refault、读取量、延迟、pgscan | 有条件通过 |

这五个受控场景证明：默认的 LSTM + reclaim-bin 可以改变回收来源；cold-aggressive 只应在冷干净页不足、冷脏页能够补缺且原生写回进度不足时短时开启。它不是适合常开的默认策略。

版本边界：受控场景 1–3 的现有正式结果来自 r7，受控场景 4–5 来自 r11；这些数值回答各自机制假设，不能直接拼成同一内核版本上的总体性能统计。R1–R7 的当前真实 GUI 正式结果则已经使用 Native 6.17.13 与 PARP r11 配对。

### 4.2 R1–R5：真实应用工作集与定向回收

R1–R5 的工作集由真实 GUI 操作形成，不使用独立匿名压力分配器来冒充应用页面。压力通过向八应用父 cgroup 写入约 256 MiB `memory.reclaim` 触发。

| 场景 | 设计意图 | 压力后的动作 | 核心指标 | 当前状态 |
|---|---|---|---|---|
| R1 `r1_app_cold_retire` | 验证退出活跃集的预测冷应用是否成为主要回收来源 | 不再返回五个冷应用 | 冷来源占比、热应用回收量、逐应用 memory drop | 通过 |
| R2 `r2_app_predicted_return` | 验证即将返回的 Firefox 是否得到保护 | 切回 Firefox，翻页并搜索固定段落 | major fault、refault、swap-in、交互动作耗时 | 通过，延迟收益较小 |
| R3 `r3_app_source_distribution` | 验证多热/多冷并存时的真实回收分布 | 依次复用 Firefox、Thunderbird、VLC | 来源占比、逐应用回收、fault/refault/swap-in、延迟 | 通过 |
| R4 `r4_app_dirty_substitution` | 尝试用真实编辑形成高代价冷工作集 | GIMP 编辑、LibreOffice 编辑保存后复用热应用 | file_dirty 门、来源、fault/refault、延迟 | 应用级选择通过；稳定 FILE_DIRTY 子机制未形成 |
| R5 `r5_app_writeback_gate` | 验证 workload-aware 页面类型选择及写回门控 | 与 R4 相同，并记录 workload profile/内核动作 | 冷热来源、anon/file 类型、fault/refault/swap、延迟、promotion | workload-aware 通过；真实 FILE_DIRTY promotion 未通过 |

R1–R5 主 bin+LSTM 三轮中位数摘要：

| 场景 | 冷来源占比 Native → PARP | 热应用回收 MiB Native → PARP | major fault Native → PARP | refault Native → PARP | 交互延迟 Native → PARP |
|---|---:|---:|---:|---:|---:|
| R1 | 72.94% → 81.62% | 70.13 → 47.94 | N/A | N/A | N/A |
| R2 | 70.52% → 79.35% | 76.49 → 53.84 | 1615 → 1232 | 1966 → 1391 | 3310 → 3261 ms |
| R3 | 72.19% → 79.60% | 72.39 → 53.04 | 2148 → 2012 | 2831 → 2302 | 5691 → 4677 ms |
| R4 | 67.52% → 78.85% | 84.42 → 55.09 | 2474 → 1772 | 3078 → 1942 | 5751 → 4720 ms |
| R5（bin-only） | 74.28% → 80.98% | 67.03 → 49.58 | 2239 → 1664 | 2832 → 1962 | 4761 → 5715 ms |

新版 R5 的 Native 与 workload-aware PARP 三轮中位数中，冷来源占比为 `71.66% → 96.49%`，热应用回收量为 `73.90 → 9.21 MiB`，热应用 major fault 为 `1398 → 1`，refault 为 `1892 → 1`，swap-in 为 `1818 → 1`。但总交互动作延迟为 `4761 → 4940 ms`，增加 3.75%，说明低层恢复指标的改善尚未稳定转化为端到端 GUI 延迟收益。

### 4.3 R6：串行 major-fault 关键路径

R6 `r6_app_serial_major_reuse` 用于解决“总 fault 降低但用户是否真的更快”这一问题。

Firefox 页面在浏览器进程内物化 384 MiB 匿名工作集，并拆成 24 个 16 MiB 块。固定训练序列后，Native 与 PARP 都向同一父 cgroup 发起 `memory.reclaim=512 MiB swappiness=max`。Firefox 返回前台后，自动化逐次点击 24 个块；下一步必须等待上一块同步访问完成并更新窗口标题，因而缺页不能被并发或固定 dwell 掩盖。

三轮中位数：

| 指标 | Native | PARP | 相对变化 |
|---|---:|---:|---:|
| 实际回收 | 511.21 MiB | 520.17 MiB | +1.75% |
| 预测热应用回收占比 | 64.64% | 2.78% | -95.70% |
| 24 步串行复用总延迟 | 6141.60 ms | 5039.91 ms | -17.94% |
| 最慢单步延迟 | 718.81 ms | 235.17 ms | -67.28% |
| major fault | 32378 | 524 | -98.38% |
| refault | 33104 | 568 | -98.28% |
| swap-in | 32976 | 568 | -98.28% |

R6 的机制与关键路径收益已经通过：PARP 回收量不低于 Native，收益不是由“少做回收”造成，而是由回收来源从预测热应用迁移到预测冷应用造成。

### 4.4 R7：公平性与故意错误预测

R7 `r7_app_fairness_misprediction` 同时观察 Firefox、Thunderbird、VLC 和 GIMP。固定序列把 GIMP 预测为极冷，压力后却故意重新使用 GIMP，构造真实的错误预测事件。

每个应用先测无压力热态响应，再测回收后的响应。定义：

```text
normalized_slowdown = post_reclaim_net_responsive_ms / warm_net_responsive_ms
normalized_responsiveness = 1 / normalized_slowdown
Jain = (Σ normalized_responsiveness)^2 /
       (应用数 × Σ normalized_responsiveness^2)
```

三轮中位数：

| 指标 | Native | PARP | 相对变化 |
|---|---:|---:|---:|
| 预测热应用回收占比 | 55.33% | 2.02% | -96.36% |
| Jain normalized responsiveness | 0.9196 | 0.9590 | +4.28% |
| 全应用最大 normalized slowdown | 1.4719× | 1.1038× | -25.01% |
| GIMP 实际回收 | 62.59 MiB | 405.29 MiB | +547.49% |
| GIMP major + refault | 8128 | 2885 | -64.51% |
| GIMP additional page-in recovery | 56.72 ms | 36.51 ms | -35.64% |

R7 证明了两点：PARP 明显保护预测热应用；当预测错误、用户返回 GIMP 时，代价确实存在，但 workload-aware 将大部分代价从匿名页换出/换入转换为干净文件页按需重读。PARP 下 GIMP 仍有 2885 次 refault，不能表述为“错误预测没有代价”。

### 4.5 R8：15 应用 memcg OOM 生存

R8 `r8_multi_app_oom_survival` 验证更强的鲁棒性问题：在 15 个真实 GUI 应用同时驻留时，由 Firefox 功能域页面在浏览器自身 cgroup 内分块申请 ArrayBuffer，触发父实验 slice 的 memcg OOM；比较 Native 与 bin+LSTM 是否能减少被杀应用数，同时保证压力发起者 Firefox 存活。

关键设计约束：

- Firefox 是唯一压力发起者，`oom_score_adj=0`；其余 14 个应用为候选 victim，`oom_score_adj=500`。
- 每个应用 scope 要求 `memory.oom.group=1`，避免只杀应用进程树中的一个随机子进程。
- `MemoryHigh=infinity`，`MemorySwapMax=1024 MiB`，ArrayBuffer 每次固定提交 64 MiB。
- 应用工作集下限按 heavy/medium/light 分层为 128/32/16 MiB，15 个应用总工作集必须至少 1536 MiB。
- OOM trace 必须能把 `mark_victim` PID 归因到压力前记录的应用 scope；出现宿主/未知 OOM、Firefox 被选为 victim、应用无 trace 消失或 trace 丢失时，本轮无效。

R8 先在 Native 上冻结压力参数：

1. 运行 3 轮无压力基线，取得父 cgroup `memory.current` 的 P95。
2. `MemoryMax` 取 `max(P95 + 1 GiB, P95 × 1.10)`，向上按 128 MiB 对齐，并受主机安全上限约束。
3. ArrayBuffer burst 从 512 MiB 起按 128 MiB 递增，每个候选运行 5 轮。
4. 只有某个候选 5 轮全部有效、压力全部提交、至少 4 轮出现 1–3 个 victim 应用且没有任何一轮超过 3 个 victim，才生成冻结配置。
5. 冻结后进行至少 10 个同 seed Native/PARP 有效配对。两侧动作计划和压力字节必须完全一致。

R8 最终判据是：10 个有效配对中，Native victim 应用总数至少为 10；PARP victim 总数相对 Native 至少降低 30%，且 PARP victim 数中位数不高于 Native。

截至本文记录时，R8 尚未生成可用于正式配对的 `READY` 校准报告和 frozen config，因此状态是“实现完成、Native 校准排障中”，不能报告 OOM 生存收益。已观察到的校准阻断包括：早期 systemd 版本不接受 `MemoryOOMGroup=yes` unit 属性、个别应用 scope 在采集中提前消失、自动化未到达工作集/压力快照、以及 prediction gate 未找到满足完整 15 应用历史的 post-marker 推理结果。这些轮次均被标记为 `BLOCKED` 或 `INVALID`，没有进入统计。

LLM 负载不属于 R8 第一阶段；配置中的 LLM runtime、GGUF、prompt 等契约仍为 deferred，不应对外描述为已安装或已验证。

## 5. 指标体系与正确口径

### 5.1 第 0 层：有效性指标

这些指标不用于说明“性能更好”，而用于决定一轮数据能否进入统计：

| 类别 | 必须满足的条件 |
|---|---|
| 环境 | 指定内核、runtime service、sudo、显示授权、应用和资产可用 |
| GUI | 窗口出现，PID、WM class、应用映射和 scope 身份一致 |
| 预测 | post-marker 历史匹配，当前应用正确，热应用排名/概率和冷应用概率过门 |
| 下沉 | PARP 组 `/dev/myfs` 成功、ABI 与绑定数正确、generation/TTL 有效 |
| 页面画像 | 工作集容量和 anon/file/file_dirty 比例满足场景门槛 |
| 压力 | 请求量、实际完成量、边界、swap 限额与双方配置一致 |
| 内核动作 | 对应策略的 `policy_hits`、`subtree_selected`、profile pass 或 promotion 非零 |
| 安全 | 无宿主 OOM、无未知 victim、无 trace 丢失、MemAvailable/PSI/超时未越界 |
| 配对 | seed、资产哈希、action-plan SHA-256 和压力字节一致 |

### 5.2 第 1 层：回收选择指标

| 指标 | 含义 |
|---|---|
| 冷应用回收量/占比 | PARP 是否把固定回收任务转向预测冷应用 |
| 热应用回收量/占比 | 即将复用应用是否被误伤 |
| 逐应用 `memory.current`、anon、file、file_dirty 下降 | 回收来源及页面类型的应用级归因 |
| `mincore()` 驻留下降 | 受控 fixture 中某一 inode/区间的精确逐出量 |
| 总实际回收量/完成率 | 排除 PARP 只是少完成回收任务的伪收益 |

真实 GUI 场景的 `memory.current` 还包含堆、共享库、缓存和应用后台线程，因此是应用级归因；只有受控 fixture 的 `mincore()` 才能提供 inode/区间级精确归因。

### 5.3 第 2 层：用户恢复成本指标

| 指标 | 含义与使用限制 |
|---|---|
| `workingset_refault_file` | 被逐出的文件页再次进入工作集，是热文件页误回收的核心信号 |
| `workingset_refault_anon` | 匿名工作集回收后再次访问的信号 |
| `pswpin` / `pswpout` | 匿名页换入/换出成本；需要与 refault、I/O 联合解释 |
| `pgmajfault` | 需要等待 I/O 的页错误，通常比总 `pgfault` 更接近用户停顿 |
| `pgfault` | 包含首次建立页表等大量 minor fault，不能单独判断收益 |
| 串行复用总延迟/最大单步延迟 | R6 中最直接的关键路径响应指标 |
| `additional_pagein_recovery_ms` | 扣除固定 200 ms 防抢跑窗口后的额外页面恢复等待 |
| `net_responsive_ms` | 从画面/操作响应跨度中扣除测试脚本主动加入的节奏 |

不要把压力准备阶段的总 fault 与压力后的用户复用窗口混在一起；前者常由工作集物化和压力分配主导，不能代表应用重返成本。

### 5.4 第 3 层：代价与效率指标

| 指标 | 用途 |
|---|---|
| `pgscan_direct` / `pgsteal_direct` | 回收扫描开销和效率 |
| PSI `some/full` | 内存压力导致任务停顿的累计时间；没有非零信号时不能宣称改善 |
| `io.stat`、块层读写量 | 判断收益是否以额外读写为代价 |
| `pswpout` | 判断策略是否把文件回收问题转化为匿名换出问题 |
| `writepage_promotions` | 证明 cold-aggressive 确实从原本不允许写回提升到允许写回 |
| `context_hits`、`rank_scores`、`subtree_selected/skipped` | 证明预测上下文和 bin 子树选择实际参与 reclaim |
| `workload_profile_misses` | 表示 profile 查找未命中，但当前未拆分未绑定 cgroup 与失效 profile，不能直接当成预测错误率 |

### 5.5 第 4 层：公平性与生存指标

| 指标 | 用途 |
|---|---|
| `normalized_slowdown` | 同一应用回收后响应相对自身热态的退化倍数 |
| Jain normalized responsiveness | 多应用响应是否均衡，越接近 1 越均衡 |
| 最大 normalized slowdown | 避免平均值掩盖最差应用 |
| unexpected-app cost | 单独报告错误预测应用的回收、fault/refault、swap-in、PSI 和恢复延迟 |
| distinct OOM victim apps | R8 的核心生存指标，按应用而不是按进程计数 |
| aggressor survived | Firefox 压力发起者必须存活 |
| host/unknown OOM、untraced disappearance | OOM 是否越出实验边界或归因链是否断裂 |

## 6. 统一验证协议

### 6.1 严格配对

每个正式 Native/PARP 对使用相同的：

- seed；
- 应用集合、启动顺序和 GUI 动作；
- 离线资产及 SHA-256；
- LSTM 历史和 dwell；
- cgroup 边界、回收或压力请求；
- 场景生成后的 `action-plan.json`。

PARP 使用 `--replay-from <Native session>` 校验动作计划哈希。哈希不同会在压力开始前直接 `BLOCKED`，不能通过事后筛选把不同工作负载拼成一对。

### 6.2 证据闭环

一个有效结论至少要同时具备：

1. 自动化 trace 证明动作实际执行且前台应用正确；
2. prediction gate 证明 LSTM 历史、概率和排名正确；
3. `/dev/myfs` 与绑定证据证明预测进入正确应用 cgroup；
4. 内核计数证明目标 reclaim 路径实际执行；
5. cgroup/mincore 证明回收对象或页面类型确实改变；
6. fault、I/O、PSI 或响应延迟证明这种改变是否转化为用户收益；
7. 安全与配对门证明结果没有越界 OOM、少做压力或动作不一致。

只满足其中一两层时，只能报告该层机制，不能向上推导用户体验结论。

### 6.3 数据统计

- R1–R7 当前正式结果主要是每组 3 个有效 seed，报告三轮原始值和中位数。
- 三轮适合做机制与方向判断，不足以声称统计显著。
- 百分比变化必须同时给出绝对值；分母接近零时不单独使用百分比。
- 离群轮次不能静默删除。只有预先定义的有效性门失败才排除，并保留 `INVALID/BLOCKED` 原因。
- R8 的正式判定要求提升到 10 个有效同 seed 配对。

## 7. 当前已经验证的问题

1. LSTM 输出能够通过 `/dev/myfs` ABI v3 与正确的应用 cgroup 绑定，并参与内核 reclaim 决策。
2. 在训练集对齐序列下，reclaim-bin 可以稳定把回收从预测热应用迁移到预测冷应用。
3. R2–R5 证明这种迁移通常能降低热应用重返时的 major fault、refault 和 swap-in，但普通 GUI 动作总延迟的改善并不总是稳定。
4. R6 通过同步、串行的 24 块匿名页复用，把约 98% 的 fault/refault/swap-in 降幅转化为 17.94% 的总关键路径缩短和 67.28% 的最慢单步延迟下降。
5. R7 已实际触发低概率 GIMP 的错误预测，并同时量化预测热应用收益、错误应用代价和多应用 Jain 公平性。
6. workload-aware 的 ANON_HEAVY、FILE_CLEAN、FILE_DIRTY、MIXED 四类路径已在受控场景中进入真实 reclaim pass；但真实 GUI 稳态只稳定复现了匿名页/干净文件页方向。
7. cold-aggressive 的收益具有条件性：写回受限且冷脏页确实能填补回收缺口时有增量收益；条件不满足时会增加扫描、swap 或 PSI。

## 8. 尚未闭环或仍需验证的问题

### 8.1 模型泛化

当前主要序列有意贴合训练集：

```text
Thunderbird → Firefox → Thunderbird → Firefox → VLC
```

因此已证明“预测正确时机制有效”，尚未证明任意真实用户序列上的 Top-k 命中率、长期平均收益和错误预测成本。后续需要加入训练集外序列、随机/半随机切换、不同用户轨迹和长时运行。

### 8.2 样本量

R1–R7 多数只有 3 个有效 seed。回收来源方向较稳定，但 GUI 延迟和 PSI 轮间波动明显。正式交付建议至少 5–10 个有效配对，并给出中位数、P95、bootstrap 置信区间和逐轮方向。

### 8.3 自动化稳定性

当前真实 PC 路径依赖 GNOME Wayland 上的 Xwayland 和 `xdotool`。窗口焦点可能被 GNOME 拒绝，应用可能出现欢迎页/对话框，窗口类和标题也可能短时变化。现有有界重试、前台校验、标题门和失败截图可以拒绝错误轮次，但不能消除重试成本。

如果下一阶段重点是跨桌面版本的语义稳定性，可把 Dogtail/AT-SPI 增加为控件级主路径，并保留 xdotool 处理无法暴露 accessibility 节点的应用；这属于后续改造方向，不是当前已实现状态。

### 8.4 真实 FILE_DIRTY 工作集

GIMP 的 GEGL swap 和 LibreOffice 保存会在稳定前被应用自身或后台写回变干净，导致真实场景中 `FILE_DIRTY` profile 与 `writepage_promotions` 不能稳定出现。当前只能用受控 fixture 验证 `FILE_DIRTY + may_writepage` 子机制，真实 GUI R5 只能证明应用冷热选择和 anon/file workload 自适应。

### 8.5 PSI 与卡顿结论

R1–R7 在约 32 GiB 环境、256/512 MiB 定向 `memory.reclaim` 下经常得到 0 PSI。没有可测 stall 时，不能用 PSI 宣称卡顿改善。需要更接近真实整机压力的 kswapd/混合负载阶段，或使用更细的前台线程/应用 cgroup stall 与首帧指标。

### 8.6 GUI 延迟口径

普通动作总延迟包含按键间隔、逐字符输入、固定 dwell、应用内部缓存和窗口管理器调度。它可能在 fault 大幅下降时仍不下降。R6 的串行页面确认、R7 的 warm/post 归一化和独立 page-in wait 更接近关键路径，后续应优先使用这些指标。

### 8.7 workload miss 的可解释性

现有 `workload_profile_misses` 同时包含“候选 cgroup 未绑定”和“已绑定 profile 无效/过期”。例如真实 R5 某轮出现 4121 次 miss，但这些 fail-closed miss 没有执行 workload 动作。计数需要按原因拆分后才能用于诊断覆盖率，不能直接解释为模型预测错误率。

### 8.8 R8 OOM 生存

R8 的代码、门禁和报告逻辑已经实现，但 Native 校准尚未冻结。当前需要先稳定 15 应用工作集、scope 生命周期和 post-marker prediction gate，再完成 Native burst 搜索，之后才能开始 10 对正式比较。在此之前不能对外声称 PARP 减少了 OOM victim 数。

### 8.9 压力外推边界

R1–R7 的 `memory.reclaim` 和 R8 的 Firefox ArrayBuffer memcg OOM 都是受控触发器。它们适合做可重复的机制比较，但不等价于无人工边界的整机长期内存压力。最终仍需要真实 PC 长时、多任务、后台写回、kswapd 和自然应用退出/重启的验证。

## 9. 对外表述边界

### 可以说明

- 预测、下沉、cgroup 绑定、bin/workload 内核动作和实际回收来源已经形成证据闭环。
- 在固定训练序列和严格配对下，PARP 能显著减少预测热应用的回收，并在 R6 中稳定降低串行 major-fault 恢复成本。
- R7 已量化多应用公平性和一次故意错误预测的代价，而不是只展示受益应用。
- cold-aggressive 是有门控、有代价的条件性策略，受控场景已经同时记录其收益条件和反例。

### 不能说明

- 不能说当前 LSTM 对任意真实用户都能保持相同收益。
- 不能把 3 轮结果表述为统计显著或产品级长期收益。
- 不能用压力阶段总 `pgfault` 代替应用重返期 fault。
- 不能在 PSI 为 0 时声称已经降低系统卡顿。
- 不能把真实 R5 表述为已经验证稳定脏文件页的 writepage promotion。
- 不能把 R6/R7 结果归因于 effective-tier 或 Tier2。
- 不能在 R8 完成冻结校准和 10 对正式实验前声称 OOM 生存改善。

## 10. 建议的下一阶段顺序

1. 完成 R8 Native 无压力基线排障，生成 `READY` calibration report 与冻结配置。
2. 用冻结配置完成至少 10 个 Native 与 bin+LSTM 同 seed 配对，先回答 victim 应用数是否降低至少 30%。
3. 将 R1–R7 扩展到 5–10 对，并增加 P95/置信区间。
4. 加入训练集外和故意错序场景，报告模型 Top-k 命中率与收益/损失联合分布。
5. 设计自然整机压力阶段，区分 direct reclaim 与 kswapd 路径，并补足非零 PSI/首帧响应证据。
6. 拆分 `workload_profile_misses` 原因，并继续保持 fail-closed。
7. 如需提高 GUI 控件级稳定性，再评估 Dogtail/AT-SPI 主路径与 xdotool fallback 的混合自动化改造。
