# PARP v4.2 全场景 full 预检记录

> 本文记录 2026-08-14 对 v4.2 执行 `hotcold full` 与 `peak full` 时的预检结果。负载未启动，因此本文不是性能指标报告。`lzx-note`

## 结论

两个 full 场景均在负载启动前被安全预检阻止，唯一未通过项是 `memory_16g_class`。

| 项目 | 当前环境 | full 契约 | 结果 |
|---|---:|---:|---|
| 内核 | `6.17.13-parp-lzx-v4.2+` | v4.2 | 通过 |
| 物理内存 | 4,065,316,864 bytes（约 3.79 GiB） | 14–18 GiB | **阻塞** |
| 可热插拔离线内存 | 0 bytes | 足以扩到 14–18 GiB | **不可用** |
| Swap | 4,087,345,152 bytes | 非零 | 通过 |
| 应用 | 15/15 已安装 | 15/15 | 通过 |
| X11、自动化工具 | 可用 | 可用 | 通过 |
| cgroup v2 memory/cpu/io | 可用 | 可用 | 通过 |
| PageFault/PARP tracepoint | 可用 | 可用 | 通过 |
| sudo 非交互授权 | 可用 | 可用 | 通过 |

这也是上一轮采用 smoke 的直接原因：当前 VMware 来宾只分配了 4 GiB，不能满足项目已经写入测试工具的 full 验收硬件契约。绕过该检查得到的数据不能标记为 full 验收结果，而且会破坏后续与 Linux 6.17.13 的同环境配对比较。
