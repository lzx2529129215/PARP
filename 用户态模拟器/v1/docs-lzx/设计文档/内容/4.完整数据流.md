
## 1. 页面进入系统

用户态模拟事件：
```text
PAGE_ADD <page_id> <cgroup_id> <ANON|FILE> <order>
```
处理过程：
```text
检查cgroup是否存在
→ 分配reclaim_page元数据
→ 设置charge_cgroup_id
→ 加入页面哈希表
→ 默认加入对应cgroup的inactive LRU尾部
→ 更新folio数和基础页数统计
→ 执行一致性检查
```

例如：
```text
PAGE_ADD 1001 1 FILE 0
```
结果：
```text
page 1001
├── charge_cgroup_id = 1
├── type = FILE
├── order = 0
├── state = ON_LRU
└── lru_kind = INACTIVE_FILE
```

## 2. 页面访问
```text
PAGE_ACCESS <page_id> <access_cgroup_id>
```
第一版 G1 只更新标记：
```text
referenced = true
last_access_seq = 当前事件序号
last_access_cgroup_id = 访问者cgroup
access_count++
```
若访问者不是页面所有者：
```text
shared = true
```
但不改变：
```text
charge_cgroup_id
LRU归属cgroup
当前链表位置
```

## 3. 页面老化
### 单cgroup
```text
AGE_GROUP 1
```
### 全局
```text
AGE_ALL
```
G1转换：
```text
inactive + referenced
→ active尾部

active + referenced
→ 刷新到active尾部

active + 未引用
→ inactive尾部

inactive + 未引用
→ 保持

完成后referenced清零
```
这一逻辑通过 `aging_ops` 实现，后续可替换为更接近Linux的传统LRU老化逻辑。

## 4. 发起定向回收

```text
RECLAIM_GROUP <cgroup_id> <target_pages>
```
例如：
```text
RECLAIM_GROUP 2 100
```
处理流程：
```text
锁定目标domain
→ 解析domain的swappiness与swap配置
→ 计算anon/file扫描比例
→ 从inactive链表头部扫描
→ 按scan_batch_pages分批隔离
→ 调用模拟执行器
→ 成功页删除
→ 失败页putback或激活
→ 达到目标或无进展后停止
```
定向回收不遍历其他cgroup。

---

## 5. 发起全局回收
```text
RECLAIM_ALL <target_pages>
```
完整过程：
```text
priority = default_priority
        ↓
按cgroup_id稳定遍历domain
        ↓
对每个domain计算effective_lru_pages
        ↓
scan_pages = effective_lru_pages >> priority
        ↓
使用swappiness拆分anon/file预算
        ↓
按批次扫描inactive LRU
        ↓
隔离候选folio
        ↓
执行回收
        ↓
累计nr_scanned与nr_reclaimed
```
如果未达到目标：
```text
priority--
→ 开始下一轮
```
退出条件：
```text
达到目标
没有可扫描页面
最低priority仍无进展
priority耗尽
执行器异常
达到最大轮数
```

## 6. 候选隔离
folio被选中后：
```text
ON_LRU
→ 从Shadow LRU摘除
→ ISOLATED
→ 加入当前candidate batch
```
此时必须满足：
```text
不再挂在任何Shadow LRU中
仍保留在页面哈希表中
charge_cgroup_id保持不变
```
如果folio大小超过剩余目标，仍整体隔离，允许产生overshoot。

## 7. 用户态模拟执行
默认：
```text
SUCCESS
```
测试可单次注入：
```text
BUSY
DIRTY
WRITEBACK
PUTBACK
ACTIVATE
UNEVICTABLE
```
处理结果：
```text
SUCCESS
→ 从哈希表删除
→ 释放元数据

BUSY / DIRTY / WRITEBACK / PUTBACK
→ 放回inactive尾部

ACTIVATE
→ 放回active尾部

UNEVICTABLE
→ 状态改为UNEVICTABLE
→ 不进入普通四链LRU
```
单次注入结果被消费后恢复为 `SUCCESS`。

## 8. 后续接入真实内核
用户态执行器将被替换为：
```text
Linux/OpenHarmony内核适配器
```
第一阶段内核接入采用保守模式：
```text
内核按原全局LRU顺序扫描folio
        ↓
查询Shadow策略信息
        ↓
判断是否：
允许隔离
暂时保护
降低优先级
        ↓
使用内核原有函数执行隔离与回收
        ↓
将结果反馈给Shadow
```
即：
```text
真实全局LRU决定“当前页面事实状态”
Shadow决定“策略上是否值得优先尝试”
vmscan决定“最终能否真正回收”
```

---

## 9. Shadow状态同步
内核阶段需要在关键生命周期点同步：
```text
folio加入LRU
folio访问
active/inactive转换
folio隔离
folio putback
folio回收成功
folio迁移
folio recharge
cgroup销毁
```
但即使进行了同步，执行前仍需再次核验真实folio状态，避免Shadow状态漂移。

## 10. 单次全局回收示例
初始：
```text
WPS inactive_file:
P1 → P2

QQ inactive_file:
P3 → P4 → P5
```
预测：
```text
WPS保护权重高
QQ回收权重高
```
请求：
```text
RECLAIM_ALL 2
```
可能流程：
```text
priority = 4
→ WPS扫描压力被降低
→ QQ获得较高扫描压力
→ 选择P3、P4
→ 两页隔离
→ P3 SUCCESS
→ P4 BUSY并putback
→ 已回收1页

priority = 3
→ 再扫描QQ
→ 选择P5
→ SUCCESS
→ 达到2页目标
→ 停止
```
