

第一版要保证：
> **任何错误都不能把哈希表、LRU链表和统计量留在半更新状态。**

因此所有公开操作都遵循：
```text
先检查
→ 再准备资源
→ 最后提交状态修改
→ 出错则保持原状态
```

## 1. 统一错误码
```c
enum reclaim_error {
    RECLAIM_OK = 0,

    RECLAIM_ERR_INVALID_ARGUMENT,
    RECLAIM_ERR_NO_MEMORY,

    RECLAIM_ERR_DOMAIN_NOT_FOUND,
    RECLAIM_ERR_DOMAIN_ALREADY_EXISTS,
    RECLAIM_ERR_DOMAIN_NOT_EMPTY,

    RECLAIM_ERR_PAGE_NOT_FOUND,
    RECLAIM_ERR_PAGE_ALREADY_EXISTS,
    RECLAIM_ERR_PAGE_STATE,
    RECLAIM_ERR_PAGE_TYPE,

    RECLAIM_ERR_PARSE,
    RECLAIM_ERR_EXECUTOR,
    RECLAIM_ERR_VALIDATION,
    RECLAIM_ERR_NOT_SUPPORTED,
    RECLAIM_ERR_INTERNAL,
};
```

函数返回错误码：
```c
int reclaim_page_add(...);
int reclaim_page_access(...);
int reclaim_age(...);
int reclaim_run(...);
```
错误码不用于表示“只回收了一部分页面”。
例如：
```text
请求回收100页
实际回收40页
```
只要流程正常完成：
```c
return RECLAIM_OK;
```
实际结果由：
```c
struct reclaim_result;
```
描述。

---

## 2. 回收结果和程序错误分开
```c
struct reclaim_result {
    enum reclaim_stop_reason stop_reason;

    uint64_t target_pages;
    uint64_t nr_pages_scanned;
    uint64_t nr_pages_isolated;
    uint64_t nr_pages_reclaimed;
    uint64_t nr_pages_putback;
    uint64_t nr_pages_activated;
    uint64_t nr_overshoot_pages;

    uint32_t final_priority;
};
```
例如页面全部 `BUSY`：
```text
函数返回：RECLAIM_OK
stop_reason：RECLAIM_STOP_NO_PROGRESS
reclaimed：0
```
这表示回收没有取得进展，但引擎本身没有发生错误。
只有执行器接口损坏、参数非法或数据结构不一致时，才返回错误码。

---

## 3. 页面加入采用“先准备、后提交”
加入folio时：
```text
检查domain存在
→ 检查page_id未重复
→ 申请page元数据
→ 初始化所有字段
→ 加入哈希表
→ 加入inactive LRU
→ 更新统计
```
如果内存申请失败：
```text
不修改哈希表
不修改LRU
不修改统计
```
避免出现只有一半状态已经建立。

---

## 4. 隔离采用可恢复转换
候选隔离：
```text
ON_LRU
→ 从LRU摘除
→ ISOLATED
→ 加入candidate batch
```
如果构建批次过程中发生错误，则把已经隔离的folio全部回滚：
```text
ISOLATED
→ 放回原LRU
→ ON_LRU
```
因此候选结构需要记录原位置类型：
```c
struct reclaim_candidate {
    struct reclaim_page *page;
    enum reclaim_lru_kind source_lru;
};
```
第一版不要求恢复到链表中的绝对原位置，失败回滚统一放回对应LRU尾部；这是明确的简化语义。

## 5. 执行器错误与页面回收失败分开
执行器返回：
```c
struct reclaim_exec_result {
    int error;

    uint64_t nr_requested;
    uint64_t nr_reclaimed;
    uint64_t nr_putback;
    uint64_t nr_activated;
};
```
### `error == 0`
执行器正常完成，即使只回收部分页面也不算程序错误。
### `error != 0`

表示执行器本身异常，例如：
- 接口没有注册；
- 批次格式非法；
- 内核适配上下文失效；
- 返回统计与批次不一致。

此时所有尚未确定结果的隔离页面都执行安全 `putback`，不能遗留在 `ISOLATED` 状态。

## 6. 文本事件解析错误
例如：
```text
PAGE_ADD abc 1 FILE 0
```
或：
```text
RECLAIM_GROUP 1
```
解析器返回：
```text
文件名
行号
事件文本
错误原因
```
示例：
```text
scenario.trace:17:
invalid page_id "abc"
```
默认行为：
```text
立即停止回放
→ 不执行错误事件
→ 保留前面已成功执行的状态
→ 执行最终一致性检查
```
后续可以增加：
```text
--continue-on-error
```
但第一版不实现，避免错误场景继续污染状态。

---

## 7. 非法生命周期操作
例如：
```text
PAGE_ACCESS 不存在的folio
PAGE_RECHARGE ISOLATED folio
重复PAGE_ADD
删除仍包含页面的cgroup
```
第一版严格返回错误，不静默忽略。
例如销毁非空cgroup：
```c
RECLAIM_ERR_DOMAIN_NOT_EMPTY
```
必须先：
```text
删除或回收所有folio
→ 再销毁domain
```

---

## 8. 一致性检查失败
如果逐事件验证发现：
```text
页面同时位于两条LRU
统计与链表不一致
ISOLATED页面仍在LRU
```
立即返回：
```c
RECLAIM_ERR_VALIDATION
```
并输出：
```text
事件序号
page_id
cgroup_id
违反的不变量
相关链表
预期值与实际值
```
这类错误被视为引擎内部bug，而不是场景输入错误。

---

## 9. 销毁引擎时的行为
正常情况下，引擎销毁前允许仍存在页面。销毁函数负责：
```text
遍历所有页面
→ 从LRU移除
→ 释放页面元数据
→ 释放domain
→ 释放哈希桶
→ 释放engine
```
如果存在 `ISOLATED` 页面，先记录警告并释放，测试模式下可将其视为验证失败。

---

## 10. 核心原则
```text
输入错误
→ 当前事件不生效

内存分配失败
→ 状态不改变

批次构建失败
→ 已隔离页面回滚

执行器异常
→ 未完成页面安全putback

部分回收
→ 正常结果，不属于程序错误

一致性破坏
→ 立即终止并报告内部bug
```
