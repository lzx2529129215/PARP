
## 1.框架结构
用户态模拟器+内核兼容接口
- 普通 `gcc/cmake` 就能编译运行；
- 可构造页面、cgroup、访问和回收事件；
- 先验证链表、状态机、统计守恒；
- 核心代码避免依赖 `malloc/pthread` 等难以移植的接口；
- 后续增加 OpenHarmony adapter。

## 2.第一版回收策略先实现传统per-cgroup LRU
每个 cgroup 维护：
```
active_anon
inactive_anon
active_file
inactive_file
```
同时预留统一的 `policy_ops` 接口，后续再加入 MGLRU backend。
优点是：
- 链路容易验证；
- 页面状态转换清楚；
- 可以先解决 cgroup、页面生命周期、候选选择和统计守恒；
- MGLRU 后续作为新策略接入，不需要重构框架。

## 3.模拟器的时间输入形式
核心先用内置场景测试（测试代码直接调用 `page_add/page_access/reclaim`，最容易调试），同时提供一个很薄的文本事件解析器

## 4.构建系统通过CMake
- 支持普通Linux和Windows开发环境；
- 容易生成静态库、模拟器、测试程序；
- 后续可以加入Sanitizer和CTest；
- 内核移植时只复制核心源码，不把CMake带入内核。

## 5.v1先实现单线程，确定性执行
- 事件按顺序处理；
- LRU链表不受并发修改；
- 每次测试结果完全可复现；
- 核心接口预留 `lock_ops`，第一版使用空锁；
- 移植内核时再映射到 `spinlock`、`mutex` 或 RCU。

## 6.页面元数据采用 哈希索引+页面内嵌LRU节点 存储
内部结构：
```
page_id
   ↓
页面哈希表
   ↓
reclaim_page
   ├── 页面属性
   └── lru_node
          ↓
对应cgroup的active/inactive链表
```

优点：
- `page_id → page` 平均接近 O(1)；
- 页面移动LRU时不需要重新分配节点；
- 页面不容易同时进入两条链；
- 后续可将用户态哈希表替换为内核 `xarray/radix tree`；
- 链表实现可以替换为内核 `list_head`；
- 页面结构职责清晰。

## 7.元数据内存通过 统一平台分配器+动态对象 进行管理
用户态模拟器映射为：
```
malloc / calloc / free
```
后续OpenHarmony内核适配为：
```
内核分配接口 / 内核释放接口
```
哈希桶数量在引擎初始化时确定，页面和 cgroup 对象按事件动态创建。

**优点：**
- 不限制模拟页面数量；
- 核心代码不直接依赖 `malloc()`；
- 用户态和内核共用同一接口；
- 可注入“分配失败”，测试异常路径；
- 后续可替换为 slab/mempool。

## 8.对于页面属于哪个cgroup的问题：
采用 **单一记账归属+单独记录访问者**
- 每个页面只属于一个 `charge_cgroup_id`
- 页面组织关系：
```
page
  └── 只挂入 charge_cgroup_id 对应的一条 LRU
```
- 访问关系：
```
其他cgroup访问文件页
  └── 更新 last_access_cgroup_id
      不改变页面的LRU归属
```
- 例如：
```
文件页 page100
charge_cgroup_id      = WPS
last_access_cgroup_id = QQ
shared                = true
```
- 含义是：
	- 页面仍由 WPS 的 cgroup LRU 负责记账和回收；
	- QQ最近访问过它；
	- 预测保护时可以考虑QQ；
	- 但不能同时把它挂进WPS和QQ两条LRU。
- 页面只有收到明确的 `PAGE_RECHARGE` 事件时，才从一个cgroup迁到另一个cgroup。
## 9.传统四链LRU的状态转换规则
使用 **确定性的“访问位+AGE事件”**

规则如下。
### 页面加入
```
ANON页面 → inactive_anon尾部
FILE页面 → inactive_file尾部
referenced = false
```

### 页面被访问
```
referenced = true
last_access_seq = 当前事件序号
```
`PAGE_ACCESS`本身不立即移动链表，避免每次访问都操作LRU链。

### 执行AGE
对页面进行状态更新：

| 页面当前状态   | referenced | AGE后的状态        |
| -------- | ---------- | -------------- |
| inactive | true       | 移入active尾部     |
| inactive | false      | 保持inactive     |
| active   | true       | 保持active，并移到尾部 |
| active   | false      | 降到inactive尾部   |
AGE处理后统一：
```
referenced = false
```

### 回收
只从inactive链表头部开始选择：
```
先扫描inactive_file或inactive_anon
→ 最老页面在链表头
→ 最近进入/刷新页面在链表尾
```
例如：
```
inactive_anon = [page1, page2, page3]

PAGE_ACCESS page2
AGE

active_anon   = [page2]
inactive_anon = [page1, page3]

RECLAIM 1
→ 首选page1
```

## 10.AGE的作用范围支持单cgroup AGE和全局AGE
```
AGE_GROUP 1
```
只老化 cgroup 1。
```
AGE_ALL
```
按稳定顺序老化所有 cgroup。
这既方便精确测试，也接近未来“按目标回收域老化”和“后台周期全局老化”两种场景。

## 11.页面选中后执行两阶段回收
```
候选选择
→ 从策略LRU隔离
→ 交给执行器批量处理
→ 返回批次统计
→ 成功页删除，失败页putback
```
其中：
- 用户态模拟器使用模拟执行器；
- 鸿蒙内核版本通过适配层接入原有回收机制；
- 我们不重写 swap、writeback、解除映射和物理页释放；
- `error` 表示适配器异常，部分页面未回收不等于执行错误。
## 12.回收请求的作用范围同时支持定向回收和全局回收
### 指定cgroup
```
RECLAIM_GROUP <cgroup_id> <target_pages>
```
例如：
```
RECLAIM_GROUP 1 20
```
表示：
```
只扫描cgroup 1
目标回收20个基础页
```
适合：
- 单独测试某个cgroup；
- 模拟memcg定向回收；
- 验证cgroup之间是否隔离；
- 后续预测明确要求压缩某个应用。

### 全局回收
```
RECLAIM_ALL <target_pages>
```
例如：
```
RECLAIM_ALL 100
```
表示：
```
系统需要回收100个基础页
→ domain_selector选择cgroup
→ 为各cgroup分配扫描预算
→ 依次回收
→ 达到目标后停止
```
这里暂时不把cgroup选择规则写死，而是预留：
```
struct reclaim_domain_selector_ops {
    int (*build_scan_plan)(
        struct reclaim_engine *engine,
        const struct reclaim_request *request,
        struct reclaim_scan_plan *plan);
};
```
第一版提供一个确定性的基线选择器，后续再替换为：
```
预测概率
+
应用前后台状态
+
workload hint
+
cgroup内存占用
+
页面冷热程度
```
共同决定扫描预算。


## 13.全局回收时采用Linux式动态扫描压力基线分配各cgroup的预算
第一版全局回收逻辑固定为：
```
RECLAIM_ALL target_pages
        ↓
从最高 priority 开始
        ↓
按 cgroup_id 稳定遍历所有 domain
        ↓
根据各 domain 的 LRU 规模计算本轮 scan budget
        ↓
分批扫描并执行回收
        ↓
累计 nr_scanned / nr_reclaimed
        ↓
达到目标则停止
        ↓
进展不足则降低 priority，扩大扫描范围
```
基础扫描量采用类似：
```
scan_pages = effective_lru_pages >> priority;
```
但第一版不会宣称完整复现 Linux 的 `get_scan_count()`，后续再加入：
```
memory.min / memory.low
历史 refault 和回收成本
active/inactive 平衡
扫描游标
预测保护量
应用和 workload 权重
```
## 14.匿名页与文件页分配采用简化的 swappiness 权重
第一版引入：
```
struct reclaim_scan_config {
    uint32_t swappiness;
    bool swap_enabled;
};
```
基本规则：
### swap不可用
```
swap_enabled = false
→ anon扫描预算 = 0
→ 只扫描file LRU
```
因为匿名页没有可用换出路径时，选择它们通常无法完成回收。

### swap可用
使用简化权重：
```
anon_weight = swappiness;
file_weight = 200 - swappiness;
```
例如：
```
swappiness = 60

anon_weight = 60
file_weight = 140
```
本轮总预算40页时，大致为：
```
anon预算 ≈ 12页
file预算 ≈ 28页
```
但还要根据实际可扫描页修正：
```
file只有10页
→ file最多扫描10页
→ 剩余预算可以转给anon
```
该版本只实现**静态权重**，暂不根据近期回收效率动态调整。
后续复杂版本再加入Linux式历史成本反馈：
```
anon_cost
file_cost
refault反馈
dirty/writeback比例
swap IO压力
各类页面实际回收成功率
```
最终逐步逼近Linux传统LRU的动态 `SCAN_FRACT` 思路。

## 15.swappiness配置作用范围为全局默认值 + cgroup可选覆盖
引擎提供默认值：
```
struct reclaim_scan_config {
    uint32_t default_swappiness;
    bool default_swap_enabled;
};
```
每个cgroup可以选择继承或覆盖：
```
struct reclaim_domain_config {
    bool override_swappiness;
    uint32_t swappiness;

    bool override_swap_enabled;
    bool swap_enabled;
};
```
例如：
```
系统默认：
swappiness = 60

WPS：
继承系统默认值60

QQ：
覆盖为20

后台下载应用：
覆盖为100
```
最终取值逻辑：
```
cgroup设置了override
→ 使用cgroup配置

没有设置override
→ 使用engine默认配置
```
这既方便第一版使用，也方便后续将预测结果动态转换成不同cgroup的扫描倾向。、

## 16.priority与扫描批次采用Linux风格，但全部可配置
默认配置：
```
struct reclaim_pressure_config {
    uint32_t default_priority;   /* 默认12 */
    uint32_t minimum_priority;   /* 默认0 */
    uint32_t scan_batch_pages;   /* 默认32 */
};
```
执行过程：
```
priority = 12
→ 扫描少量页面
→ 回收不足

priority = 11
→ 扫描范围扩大
→ 回收仍不足

……

priority = 0
→ 扫描压力最大
```
每次实际处理不超过：
```
scan_batch_pages = 32个基础页
```
小规模测试中可以覆盖配置，例如：
```
.default_priority = 4,
.minimum_priority = 0,
.scan_batch_pages = 4,
```
否则模拟器只有几十页时：
```
40 >> 12 = 0
```
不便于观察行为。

当计算结果为0，但当前仍有可扫描页且目标尚未达到时，第一版可使用：
```
scan_pages = 1;
```
保证每轮至少产生一次扫描尝试。

### 优点
- 框架与Linux传统回收接近；
- 正式配置可以使用 `12 → 0`；
- 小场景测试可使用较小priority；
- 批次大小后续可以映射到内核扫描批次；
- 不把常量散落在算法代码中。

## 17.全局回收结束时机：每个priority完整遍历一轮，并设置明确终止条件
- 每个priority一轮完整遍历，达到目标立即停止；耗尽priority、无可扫描页、最终无进展或执行器异常时退出，并设置最大轮数保险
执行规则：
```
priority = default_priority

遍历所有cgroup
→ 扫描和回收
→ 统计本轮 scanned / reclaimed

达到target
→ SUCCESS，立即停止

未达到target
→ priority降低一级
→ 下一轮扩大扫描压力

到达minimum_priority并完成最后一轮
→ 停止
```
同时设置以下退出原因：
```
enum reclaim_stop_reason {
    RECLAIM_STOP_TARGET_REACHED,
    RECLAIM_STOP_NO_SCANNABLE_PAGES,
    RECLAIM_STOP_NO_PROGRESS,
    RECLAIM_STOP_PRIORITY_EXHAUSTED,
    RECLAIM_STOP_EXECUTOR_ERROR,
    RECLAIM_STOP_ROUND_LIMIT,
};
```
并加入保险参数：
```
uint32_t max_reclaim_rounds;
```
默认可设为：
```
default_priority - minimum_priority + 1
```
例如 `12 → 0`，最多13轮。

### 无进展判断
完成一整轮cgroup遍历后：
```
nr_scanned = 0
→ 没有可扫描页面
→ NO_SCANNABLE_PAGES

nr_scanned > 0 且 nr_reclaimed = 0
→ 页面都无法回收
→ 可以继续降低priority
→ 到minimum_priority仍无进展则NO_PROGRESS
```
这样既能逐步增加压力，又不会无限扫描脏页或busy页。

## 18.模拟执行器显式指定模拟结果
- 用户态阶段默认回收成功，并支持显式失败注入；
- 进入Linux或OpenHarmony内核后，模拟执行器被真实内核执行适配器替换，回收结果由原有内核机制产生
用户态模拟器不应重新模拟完整的 Linux 页面回收机制，否则容易把测试模型误当成真实内核行为。

页面默认回收成功：
```
PAGE_ADD 1001 1 FILE 4096
RECLAIM_GROUP 1 1
```
结果：
```
page 1001 → 模拟回收成功
```
测试失败和放回路径时，显式设置结果：
```
PAGE_EXEC_OUTCOME 1001 BUSY
PAGE_EXEC_OUTCOME 1002 WRITEBACK
PAGE_EXEC_OUTCOME 1003 UNEVICTABLE
PAGE_EXEC_OUTCOME 1004 ACTIVATE
```
支持的模拟结果：
```
enum reclaim_sim_outcome {
    RECLAIM_SIM_SUCCESS,
    RECLAIM_SIM_PUTBACK,
    RECLAIM_SIM_ACTIVATE,
    RECLAIM_SIM_BUSY,
    RECLAIM_SIM_DIRTY,
    RECLAIM_SIM_WRITEBACK,
    RECLAIM_SIM_UNEVICTABLE,
};
```
处理规则：

|模拟结果|页面处理|
|---|---|
|`SUCCESS`|删除页面元数据，增加 `nr_reclaimed`|
|`PUTBACK`|放回原 cgroup 的 inactive 尾部|
|`ACTIVATE`|放入对应 active 尾部|
|`BUSY`|放回 inactive，增加 `nr_busy`|
|`DIRTY`|放回 inactive，增加 `nr_dirty`|
|`WRITEBACK`|放回 inactive，增加 `nr_writeback`|
|`UNEVICTABLE`|标记不可回收，不再作为普通候选|

这样模拟器只负责验证：
```
候选选择是否正确
→ 隔离是否正确
→ 批次统计是否正确
→ 成功页面是否删除
→ 失败页面是否正确putback
```
它不会假装实现真实的 swap、writeback、unmap 和页面释放。

## 19.`reclaim_page` 代表 一个对象表示一个 folio
```
struct reclaim_page {
    uint64_t page_id;
    uint32_t order;
};
```
其基础页数量为：
```
nr_base_pages = 1ULL << order;
```
例如：

|`order`|表示的基础页数|按4 KiB计算|
|---|---|---|
|0|1|4 KiB|
|1|2|8 KiB|
|2|4|16 KiB|
|9|512|2 MiB|
回收目标、扫描量和统计都用**基础页数量**：
```
RECLAIM_GROUP 1 100
```
表示目标回收100个基础页，而不是100个folio。
第一版将整个folio作为一个不可拆分对象：
```
选中该folio
→ 整个folio被隔离
→ 整体成功或整体putback
```
暂不实现大folio拆分和部分回收。

## 20.大folio导致目标超额时，允许超额回收，不拆分folio
直接选择整个folio：
```
剩余目标：100页
候选folio：512页
→ 隔离整个folio
→ 成功后回收512页
→ 最终超过目标412页
```
结果中记录：
```
result.target_pages = 100;
result.nr_reclaimed_pages = 512;
result.nr_overshoot_pages = 412;
```
优点：
- 保持folio不可拆分语义；
- 不会因为folio太大而长期跳过它；
- 算法简单、结果确定；
- 后续接入内核时更自然。

## 21.测试模式下每个事件后自动检查数据结构一致性
提供统一函数：
```
int reclaim_engine_validate(
    const struct reclaim_engine *engine,
    struct reclaim_validation_report *report);
```
它检查至少以下不变量：
1. 每个folio最多挂在一条LRU；
2. `ON_LRU` 页面必须属于有效cgroup；
3. LRU所在cgroup必须等于 `charge_cgroup_id`；
4. `ISOLATED` 页面不能还在LRU中；
5. 已回收页面不能再出现在哈希表中；
6. anon页只能进入anon链，file页只能进入file链；
7. active状态与active链一致；
8. 每条LRU记录的folio数、基础页数与实际遍历结果一致；
9. 全局统计等于所有cgroup统计之和；
10. 哈希表中的所有页面必须且只能处于一种合法生命周期状态。
测试和事件回放时默认：
```
每处理一个事件
→ 自动执行validate
→ 发现错误立即报告事件行号并停止
```
普通性能运行时可以关闭逐事件检查，只在结束时检查一次：
```
--validate-each-event
--validate-at-end
--no-validate
```

## 22.folio生命周期状态：采用显式生命周期状态机
明确一个 folio 当前究竟处于什么阶段，防止它同时出现在 LRU、隔离集合或已删除状态中。
```
enum reclaim_page_state {
    RECLAIM_PAGE_NEW,
    RECLAIM_PAGE_ON_LRU,
    RECLAIM_PAGE_ISOLATED,
    RECLAIM_PAGE_UNEVICTABLE,
};
```
合法转换为：
```
PAGE_ADD
NEW → ON_LRU

候选隔离
ON_LRU → ISOLATED

回收失败
ISOLATED → ON_LRU

重新激活
ISOLATED → ON_LRU（进入active链）

判定不可回收
ISOLATED → UNEVICTABLE

回收成功
ISOLATED → 从哈希表删除并释放元数据
```
不保留长期的 `RECLAIMED` 对象，因为回收成功后元数据已经释放；回收统计单独记录。
非法操作示例：
```
ISOLATED页面再次隔离
UNEVICTABLE页面进入普通inactive链
ON_LRU页面同时挂入两条链
不存在的页面执行PAGE_ACCESS
```
这些都会返回明确错误，并由一致性检查器发现。
